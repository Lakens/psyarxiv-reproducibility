How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold” or “legend”). Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Proliferating web-based experimentation platforms have substantially broadened access to cognitive psychology research infrastructure, yet no existing tool simultaneously supports continuous and trial-based paradigms, maintains institutional data-protection compliance, works across online and laboratory settings, and operates within the constraints of collaborative multi-site teams. We present CogFlow, a free, open-source, self-hostable web platform for constructing, deploying, and managing cognitive psychology experiments. CogFlow's JSONcentric architecture uses a single declarative configuration file to specify both study design and runtime instructions for the Interpreter engine, supporting a broad task library including Random Dot Motion, Flanker, SART, Stroop and Emotional Stroop, Simon, Task Switching, PVT, MOT, N-back, Gabor patch, Continuous Image Presentation, and Security Operations Centre (SOC)-style multitask environments, in both trial-based and continuous-presentation modes. A no-code graphical Builder lowers the barrier to experiment authoring while preserving full parameter-level configurability for researchers who require it; results are collected as encrypted payloads with multi-factor authentication gating and pseudonymised participant linkage, supporting compliance with GDPR, UK GDPR, and IRB data management requirements. The platform integrates 1 natively with SONA Systems and Prolific Academic for participant recruitment, provides in-portal descriptive analysis and charting, and includes a CogFlow To Go packaging mode for offline laboratory deployment with Lab Streaming Layer (LSL) support for physiological co-registration. Software-layer runtime benchmarks confirm stable performance consistent with the broader literature on browser-based platforms. CogFlow is available at https://cogflow.app under the BSD 3-Clause licence; contributor roles are tracked using the CRediT taxonomy with versioned archival via Zenodo.

1 Introduction

The design and delivery of cognitive psychology experiments increasingly takes place in web-based environments, a shift accelerated by the practical demands of largescale online data collection and the recognised advantages of browser-delivered stimuli for accessibility, sample diversity, and replication across sites (e.g., Bridges, Pitiot, MacAskill, & Peirce, 2020). A range of platforms now exists to support this workflow, from full-featured desktop solutions with online export pathways such as PsychoPy and Pavlovia (Peirce et al., 2019) to browser-native frameworks including jsPsych (de Leeuw, Gilbert, & Luchterhandt, 2023) and lab.js (Henninger, Shevchenko, Mertens, Kieslich, & Hilbig, 2022), and server-managed experiment management systems such as JATOS (Lange, Kühn, & Filevich, 2015). Each of these tools has contributed meaningfully to the methodological infrastructure of the field, yet none addresses the complete set of requirements that characterises modern cognitive research programmes operating at institutional scale.

Specifically, several gaps remain underserved across existing platforms when they are considered individually. No-code authoring environments typically sacrifice configurability, while fully code-based frameworks require programming competence that not all research teams possess, particularly in supervisory or multi-investigator contexts. Participant recruitment integrations, in-platform data inspection, and offline laboratory deployment with physiological co-registration are each addressed by separate tools or custom workflows, fragmenting the research pipeline and increasing the technical overhead associated with each new study. Data security and institutional compliance infrastructure is frequently left to the researcher or their IT department to arrange independently, creating variable and often undocumented data-protection practices across studies. And while open-source licensing is common, sustainable collaborative attribution frameworks that allow contributors -whether co-investigators, research assistants, or external developers -to formally claim and cite their roles in platform development remain rare.

CogFlow (see Figure 1) was designed to address these gaps within a single, coherent, free-to-use platform. Its architecture is organised around a JSON-centric core in which a single declarative configuration file serves simultaneously as the humanreadable specification of a study and the runtime instruction set for the Interpreter engine, while participant results are returned in a separate JSON container whose payload is encrypted at ingestion. This design improves replicability, facilitates preregistration alignment, and keeps deployment lightweight. A no-code graphical Builder supports experiment authoring across a broad paradigm library, with explicit support for both trial-based and continuous presentation modes and granular parameter control at the block level; researchers with programming expertise can inspect and modify the underlying JSON directly, preserving ultimate flexibility without imposing it as a requirement. Production-grade security measures -including Fernet-symmetric payload encryption, salted SHA-256 participant pseudonymisation, MFA-gated decrypt access, and immutable audit logging -are built into the platform codebase rather than delegated to institutional infrastructure, designed to support compliance with the General Data Protection Regulation (GDPR), UK GDPR, and Institutional Review Board (IRB) data management expectations out of the box. Native integrations with SONA Systems and Prolific Academic streamline participant recruitment; an in-portal Analysis module provides preliminary descriptive reporting and charting before data are downloaded; and a CogFlow To Go packaging mode enables offline laboratory deployment with Lab Streaming Layer (LSL) support, extending the same study configurations to settings that require physiological co-registration or guaranteed network independence. The platform is free to use in perpetuity, self-hostable for institutions requiring data sovereignty, and supported with a documented response commitment for researcher queries.

This paper introduces the CogFlow platform to the cognitive psychology research community, available publicly at https://cogflow.app. Here, our focus is the design features of the CogFlow platform rather than a tutorial describing use cases of the platform; the latter is available at a dedicated and up-to-date section of the CogFlow website. To foreshadow the motivating design features of CogFlow, Table 1 provides a feature-level comparison with representative extant platforms. Existing platforms provide many of the individual capabilities implemented in CogFlow, but differ in how these capabilities are combined and in the extent to which they form part of an integrated research workflow. Rather than being distinguished by any single capability, CogFlow is distinguished instead by the intersection of features that are typically distributed across different experimental workflows. In particular, it brings experiment authoring and deployment together with data management, recruitment, laboratory use, analysis, security, and collaborative research infrastructure within a single platform.

The paper is structured as follows. We first describe the JSON-centric architecture that underlies the platform's design (2.1), the Builder authoring environment (2.2), the Interpreter engine and its support for standard and bespoke paradigms (2.3), the in-portal Analysis module (2.4), participant recruitment integrations (2.5), CogFlow To Go offline deployment mode (2.6), and the security and compliance infrastructure (3). We report software-layer runtime benchmarks characterising the platform's timing performance across network conditions (4), user roles and associated privileges (5), and platform availability and contributions (6). We close with a discussion of current scope, planned development, and the platform's position relative to existing tools (7).

2 Technical specifications

2.1 JSON-centric Architecture

The JSON format occupies a central and load-bearing role throughout the CogFlow architecture, serving simultaneously as the medium for experiment specification, runtime instruction, and participant data capture. During study design and timeline construction, CogFlow Builder exports a structured JSON configuration object that encodes every parameter required to instantiate a study: top-level fields for experiment type (trial-based or continuous), task scope, data-collection toggles, and UI settings, together with a timeline array that composes individual components, generative Block definitions, structural loop markers, and randomisation-range markers into a complete, declarative description of a session. This JSON config file is open to sharing and redistributing both for ease of collaboration and for enhancing transparency and replicability of studies: by importing a JSON into a new study, a researcher can easily run a separate iteration of the same paradigm on a separate set of participants. The config is therefore the single artefact that moves from researcher intent to live deployment -it is published to the platform backend, versioned as a ConfigVersion record, and later retrieved by the Interpreter engine to compile the jsPsych timeline without any further researcher intervention.

On the data-collection side, the JSON file format also plays the central role: at the close of each participant run, the Interpreter assembles a result payload, also in JSON format, that carries the full trial-level behavioural record -response times, accuracy flags, stimulus metadata, and any task-specific fields such as gaze samples -and transmits that payload to the backend via a dedicated submission endpoint. Critically, the raw payload is not stored in plain text; it is encrypted server-side at the point of ingestion, so the JSON object that enters durable storage is an encrypted envelope whose plain text is inaccessible without an authenticated, MFA-verified decrypt operation. 2 "Ready paradigms" refers to complete or near-complete implementations of cognitive tasks that can be deployed or adapted, rather than lower-level components or plugins used to construct experiments.

3 "Online management" refers to integrated hosting of deployed experiments and server-side management of participant data within the platform or its associated ecosystem.

4 "Recruitment" refers to built-in support for linking studies with participant recruitment systems such as SONA, Prolific, or MTurk, rather than recruitment through independently configured external workflows.

5 "Lab deployment" refers to support for running experiments locally or offline rather than requiring access to the platform's online service. Native physiological integration is noted where applicable.

This design places JSON at the intersection of three architectural concernsstudy specification, runtime execution, and secure data stewardship -and means that any researcher familiar with JSON can inspect, validate, or version-control their study definitions with ordinary text tooling, while the confidentiality of participant data is protected independently of that transparency.

2.2 CogFlow Builder

The Builder supports the construction of both trial-based and continuous paradigms using a visual, component-based authoring environment (an example of the UI viewport can be seen on Figure 2). Experiments are assembled by adding configurable components (Figure 2C) to a graphical timeline (Figure 2D) representing the sequence of events within the experiment. Components can be reordered, grouped, and nested within experimental blocks, allowing researchers to construct complex task structures without custom programming. A task-scoped component library provides elements for stimuli, responses, feedback, breaks, surveys, randomisation, loops, save checkpoints, secondary tasks, and thought probes, while complete study configurations are stored as JSONs that can be exported, versioned, reloaded, or published directly to the CogFlow platform. Researchers may begin from existing task templates or construct paradigms from individual components while retaining parameter-level control over stimulus properties, response modalities, timing, and block structure. The Builder supports continuous stimulus presentation within the same visual authoring environment used for trial-based paradigms. For instance, the Builder encodes the random dot motion task in both its canonical discrete-trials format (one response per trial, categorising stimulus identity) and a novel continuous-display format (multiple responses on the basis of changes in stimulus identity). In both trial formats, researchers can configure all aspects of the random dot motion stimulus through the interface, including coherence, motion direction, dot lifetime, speed, dot density, colour, noise characteristics, and the properties of two independently configurable dot groups, without requiring custom programming. The Builder therefore provides a common authoring environment across paradigms that differ substantially in experimental structure and appearance, including continuous tasks, discrete trialbased tasks, secondary or auxiliary tasks, questionnaires, and thought probes, all constructed using the same component-based interface, allowing these elements to be combined within a single experimental configuration.

The Builder also supports experimental components that operate independently of the primary task structure. Secondary tasks, including Detection Response Tasks (DRTs), can be configured to begin and end at predefined points within an experiment, allowing them to operate continuously across multiple task blocks. Similarly, thought probes, such as those used in the study of task-unrelated thoughts, can be scheduled at configurable intervals independently of task events, while questionnaires may be inserted at any point within the experimental workflow. Loop and randomisation controls are implemented directly within the timeline, allowing sections of an experiment to be repeated or shuffled without duplicating components. Configurable save checkpoints preserve participant data throughout an experiment, reducing data loss resulting from participant attrition or unexpected interruptions during online testing. Completed studies can be previewed before deployment, and published configurations can subsequently be reloaded and modified without reconstructing the experiment, supporting rapid iteration throughout the development process.

2.3 CogFlow Interpreter Engine

The CogFlow Interpreter is a self-contained, browser-side JavaScript runtime that consumes a Builder-exported JSON configuration and compiles it into an executable jsPsych timeline, orchestrating the full sequence of stimulus presentation, response capture, and data submission without requiring any server-side rendering or real-time backend involvement during the experiment itself. The engine is organised as a small set of loosely coupled JavaScript modules: • configLoader.js handles the resolution of experiment configurations from multiple possible sources (the platform's Django backend, a Cloudflare-hosted Token Store, a local file system via URL parameters, or a direct file-upload fallback); • timelineCompiler.js is the primary compilation engine, traversing the JSON timeline array and expanding each item -standard jsPsych components, generative Blocks, loop-marker pairs, and randomisation-group pairs -into concrete jsPsych trial objects; and • main.js provides the top-level orchestration that sequences loading, compilation, execution, and result submission.

Each cognitive task is implemented as a self-contained jsPsych plugin (e.g., jspsych-rdm.js, jspsych-sart.js, jspsych-gabor.js, jspsych-stroop.js, jspsych-pvt.js, jspsych-nback.js, jspsych-mot.js, jspsych-task-switching.js), loaded as browser globals and consumed by the compiler purely by type key. This architectural pattern means that new paradigms can be added by supplying a new plugin file and registering its type key in the compiler, without modifying any of the core loading or submission infrastructure, conferring a high degree of extensibility and making the Interpreter straightforwardly portable to institutional servers, JATOS deployments, or standalone hosting environments without modification to its JavaScript source. In addition to the engine run outside of the main portal interface when delivered straight to participants, the CogFlow portal also allows a Preview of any published study in a dedicated space, as seen in Figure 3. Beyond the standard trial-based compilation path, the Interpreter includes dedicated engines for bespoke continuous paradigms that cannot be adequately captured by a simple per-trial compilation loop. Among such paradigms are tasks like the security operations centre (SOC) Dashboard and Continuous Image Presentation (CIP).

The SOC Dashboard (jspsych-soc-dashboard.js) renders a simulated multiwindow "security operations centre" desktop environment as a single extended jsPsych session, within which up to four simultaneous subtask windows -each implementing a distinct cognitive demand modelled on sustained attention to response (SART), N-back, Flanker, Wisconsin card sorting test (WCST), or psychomotor vigilance task (PVT) paradigms -can be scheduled to appear, overlap temporally, and dismiss according to researcher-specified timing parameters. All trial-level events from all active subtasks are written into a unified, timestamped events array in real time, giving researchers a fine-grained behavioural record that preserves the temporal relationships among concurrent task demands.

Continuous Image Presentation paradigm similarly uses a purpose-built plugin (jspsych-continuous-image-presentation.js) that sequences a list of assetbacked images with configurable durations and sprite-based masking transitions, compiled from block-level parameter values that the Builder resolves to fully-qualified asset URLs at export time.

For continuous-mode tasks generally, the compiler converts researcher-specified block durations in seconds into frame counts using the experiment-defined frame rate, ensuring that timing is preserved independently of trial-count parameterisation. Together, these purpose-built engines coexist with the general-purpose plugin architecture without introducing coupling, so the modularity of the codebase is not compromised by the complexity of the paradigms it supports.

2.4 CogFlow Analysis Tab

CogFlow includes a built-in Analysis module within the researcher portal that is designed to support rapid, in-platform inspection of study data prior to full export and offline analysis (Figure 4). The module operates as an on-demand asynchronous report pipeline: a researcher selects a study, specifies an analysis engine (Python or R), and issues a report request; the backend queues a StudyAnalysisReportJob, which a background worker then claims, processes, and resolves against the study's decrypted trial-level records. The resulting report is generated in multiple output formats simultaneously -Markdown, HTML, PDF, and, when the R engine is selected, an R Markdown document -and stored as versioned StudyAnalysisReportArtifact records that the researcher can subsequently browse or download from the portal.

The report content is structured around a set of configurable report sections. This includes an overview of run counts and completion status, field-coverage diagnostics summarising which variables were captured and with what density, a numeric summary of behavioural variables of interest computed with descriptive statistics (mean, SD, min, max, and sample size) across all completed runs, and optionally a per-participant summary. Variable selection is driven by a keyword-matching system seeded with taskfamily defaults (targeting fields such as reaction time, accuracy, correctness, score, and response), which a researcher can override at report-generation time; a priority ranking ensures that core behavioural outcomes appear prominently while configuration-level metadata fields are deprioritised. A supplementary chart builder, operating separately from the report artifacts, allows researchers to select variables from the report and generate aggregate bar charts with standard-deviation error bars, providing an immediately legible visual impression of the dataset before any data are downloaded. Together, the report and chart tools are intended to serve early-stage study monitoring rather than replace dedicated statistical software. Their primary utility is in helping researchers gauge participant engagement, identify obvious data-quality signals, and make informed decisions about whether to continue, adjust, or terminate data collection, all without leaving the platform or decrypting the full result payload locally.

2.5 CogFlow Integrations: SONA, Prolific, and More

CogFlow integrates natively with two of the most widely used participant recruitment platforms in academic cognitive psychology research, SONA Systems and Prolific Academic, via a dedicated Integrations module in the researcher portal (Figure 5). Both integrations follow the same general pattern: the researcher selects a study, configures platform-specific parameters, and the portal generates a complete, ready-to-paste external study URL that embeds the appropriate participant-tracking placeholders. For SONA, the generated link accepts an optional fixed participant code or leaves the identifier field unpopulated for automatic resolution, and the researcher supplies a SONA completion URL -formatted to the SONA credit-granting web study schema -along with an optional abort URL for incomplete runs; the platform supports the placeholder tokens participant external id, participant key, and run session id in both URLs, enabling automatic credit granting and participantlevel linkage on return from CogFlow. For Prolific Academic, the portal generates an external study URL that embeds the standard Prolific URL parameters ({{PROLIFIC PID}}, {{STUDY ID}}, and {{SESSION ID}}), with configurable completion behaviour set to auto-redirect to the Prolific completion page by default. Both link generators are study-scoped and share the same study-selection control, and both support the use of saved study-flow variants for counterbalanced assignment, so researchers running multi-task or counterbalanced designs can configure variant routing once and have recruitment-platform links automatically reflect the correct assignment logic. Beyond these built-in integrations, the platform's open API and modular link-generation architecture mean that any recruitment system capable of appending URL parameters to an external study link -including institutional custom panels, REDCap-mediated pipelines, or bespoke in-house systems -can be connected without modification to the platform codebase.

2.6 CogFlow To Go: Offline and Laboratory Deployment with LSL Support

CogFlow To Go is a self-contained local deployment mode that allows researchers to run any CogFlow study entirely offline, without a network connection to the platform or any external service, while retaining full compatibility with the same JSON-driven paradigm configurations and data pipeline used in online deployments.

From the portal, a researcher selects a study, configures bundle options, and clicks to prepare and download a bundle archive; the backend assembles the bundle via the StudyTakeToGoBundleView endpoint, packaging the Interpreter runtime together with the study's published configuration JSON and any associated assets into a selfcontained directory that can be unzipped and launched on any target machine (see the UI in Figure 6). The bundle includes platform-specific launcher scripts (run-kiosk.sh for Linux, Run Kiosk.command for macOS, and run-kiosk.bat for Windows) that start the necessary local services and open the Interpreter in a kiosk-mode browser window at http://127.0.0.1:8888, requiring minimal technical setup from the person running the session beyond a local Docker installation. All CogFlow To Go deployments store data at known destinations. Interpreter metadata JSONs are stored inside the bundle at a known path (interpreter/metadata/), participant run exports are saved as JSON or CSV files to the browser's default Downloads folder when the debug/download flag is active, and -crucially for laboratory settings -a Lab Streaming Layer (LSL) bridge container is included in the bundle that emits event markers and persists behavioural result files into a local results/ directory via a Docker volume mount, enabling synchronised co-registration with physiological recording systems such as EEG amplifiers. The bridge is implemented with pylsl, and three LSL system profiles can be selected at bundle-generation time: Generic LSL, BioSemi, and Brain Products. These profiles have not yet been extensively verified against the corresponding acquisition systems, and full validation of the LSL stream against hardware is planned as part of upcoming laboratory pilot deployments; the current release provides the architectural integration and bundle infrastructure, and empirical characterisation of LSL timing and marker fidelity will be reported in a subsequent communication.

3 Security Measures Ensuring Confidentiality and Safety of Data Transmission

CogFlow's security model is designed around the recognition that participant behavioural data constitutes sensitive research output subject to institutional ethical oversight, and that a platform intended for broad adoption across research groups must provide technically credible data-protection controls that can be directly cited in ethics board submissions and data management plans. The architecture implements protection at several distinct layers (see the schematic flow of the data governance policies in Figure 7 or at https://cogflow.app/security). At the transport layer, all communication between participant browsers and the platform is conducted exclusively over HTTPS/TLS, preventing interception of in-flight data during the execution of the study or the submission of the results. At the ingestion layer, result payloads submitted by the Interpreter are encrypted server-side at the point of write, before any persistence to the database, using symmetric Fernet encryption (implemented in security.py) with keys supplied via environment variables and enforced to be non-default in any non-debug deployment; the encrypted ResultEnvelope record is the unit of durable storage, meaning that the underlying behavioral data are never held in plaintext in the database. Participant identifiers follow a pseudonymisation model: rather than storing raw external identifiers, the backend derives a salted SHA-256 hash of each participant ID at session creation time using a configurable salt value (hash identifier in security.py), so that database records cannot be directly linked to individuals by anyone who does not also hold the salt. Anonymous launches are supported natively, with the backend generating a random UUID-based identifier for sessions that carry no external participant token, preserving counterbalancing properties across runs while avoiding any linkage risk. Access to decrypted data is controlled through a multi-factor authorisation pathway. Researcher access to result payloads requires an authenticated session, role-scoped and organisation-scoped authorisation, and a recent MFA verification window; the decrypt endpoint (POST /api/v1/results/decrypt) enforces these checks server-side on every request and records the outcome -including denied attempts -as an immutable AuditEvent row, capturing actor, action type, target resource, timestamp, and request metadata. Privileged administrative operations such as role assignment, account deletion, study ownership transfer, and destructive deletions are governed by a formal security matrix requiring authorisation by the platform administrator role, which is reserved for the CogFlow team and never assigned to users, mandatory MFA enrollment, step-up MFA verification with a bounded freshness window, and perpetual audit logging; the matrix is explicitly enforced in the backend handlers rather than relying on frontend route visibility as a control.

The platform's compliance posture is designed to be consistent with the requirements of major research data-governance frameworks, including GDPR (EU 2016/679), UK GDPR, IRB data management plan expectations, and Australian data governance frameworks, with the Ethics and Compliance module inside the researcher portal providing copy-ready paragraphs mapped to specific data-protection dimensions for direct use in ethics board submissions. The full end-to-end governance flow -from researcher authentication and study configuration through participant submission, server-side encryption, controlled decrypt, audit logging, and retention management -is documented publicly at https://cogflow.app/security, providing transparency suitable for institutional review while not disclosing internal operational details.

4 Runtime Performance

We first benchmarked the timing precision of CogFlow's Interpreter, which compiles and executes experiments as a jsPsych v8.2.3 timeline (de Leeuw et al., 2023). A dedicated probe experiment, run directly in a headed Chromium environment, presented a 300 ms blank inter-trial interval (ITI) followed by a 200 ms stimulus, with a Playwright-dispatched Space keypress fired exactly 100 ms after stimulus onset. Each session comprised 200 trials (the first 5 discarded as warm-up) and the probe was repeated 20 times, yielding 4,000 measurement trials in total. Reaction-time precision was taken as the trial-to-trial variability (SD) of recorded response latency, and timer accuracy as the trial-to-trial variability (SD) of the deviation of the measured ITI duration from its nominal 300 ms value; the mean precision index is the average of these two SDs. Table 2 reports these measures alongside the corresponding published values for jsPsych v6 (Bridges et al., 2020). The CogFlow values are numerically smaller than those reported for the best-performing jsPsych v6 configuration in that study (macOS/Safari: 0.66 ms RT precision SD, 3.39 ms mean precision), but the two sets of figures are not directly comparable. The published measurements (Bridges et al., 2020) were obtained with a Black Box Toolkit, a 1 kHz MilliKey button box, and a photodiode, i.e., hardware-validated photon-onset timing, whereas the CogFlow probe measures timing internal to the browser's performance.now() model and therefore does not capture variability introduced downstream of the browser, such as display refresh and input-device polling. The +2 ms RT lag most likely reflects Playwright's keyboard-dispatch overhead rather than jsPsych itself, and physical keyboards add latency of their own that this probe does not measure. The values in Table 2 should therefore be read as characterising the timing noise of the Interpreter's software layer, not as estimates of end-to-end precision, which still requires hardware validation on the target setup.

5 User Roles and Privileges

In this section, we outline representative usage scenarios for CogFlow's four platform roles: researcher, analyst, instructor, and student. Although the underlying study infrastructure is shared across all four roles, the platform's permission model governs what each role can author, share, and view, allowing classroom deployments and multi-investigator labs to coexist safely within the same portal. A fifth, platform administrator role is reserved for the CogFlow team and is never assigned to users; it is therefore not discussed further here. Table 4 summarises the actions available to each role; the paragraphs below describe how these translate into everyday workflows.

Researchers represent the platform's primary authoring role and correspond to principal investigators, postdocs, or graduate students running independent projects in cognitive psychology, mathematical psychology, and psychophysics. A researcher designs a task in the Builder, validates its timing and logic, and publishes it, which creates a study record together with its first configuration version; the resulting participant link can then be distributed directly or routed through a recruitment pipeline such as Prolific. Because a researcher owns every study they publish, they retain full control over that study's collaborators: access can be granted to, or revoked from, individual co-investigators or analysts, ownership can be reassigned if project staffing changes, and the granularity of what a given collaborator sees, ranging from full per-participant runs down to aggregate summaries only, is set by the owner on a per-collaborator basis. Analysts occupy a narrower, results-facing role suited to statisticians, research assistants, or external collaborators who need to work with study data without taking on authoring or governance responsibilities. An analyst cannot create or publish studies; instead, they gain visibility into a study only once its owning researcher explicitly shares it with them. By default, that shared access is scoped to aggregate-level summaries rather than individual response rows, letting a lab bring in outside collaborators for statistical support while keeping raw, potentially identifying behavioral data restricted to the study owner unless broader access is deliberately granted.

Instructors hold the same authoring privileges as researchers, including designing, validating, publishing, and sharing their own studies, and additionally take on the platform's teaching layer. From Account Settings, an instructor can create a named course section, which generates a revocable enrollment code and a roster of enrolled students. Any study a student attaches to that section during publishing automatically grants the instructor a course-collaborator view of that study, so reviewing student work does not require the instructor to individually request or wait for sharing from each student. This arrangement is deliberately limited to review access: it does not transfer study ownership or give the instructor control over how a student shares that study with anyone else.

Students hold essentially the same study-authoring capabilities as researchers: they can design tasks in the Builder, and validate, publish, and share studies with collaborators of their choosing. What distinguishes the student role is its tie to coursework: students register with an enrollment code supplied by an instructor, may join additional active sections later from Account Settings, and can optionally attach a published study to the section they belong to. Attaching a study to a section is what activates the instructor's automatic review access described above, making the student and instructor workflows two halves of the same classroom pipeline.

7 Discussion

7.1 Intended Scope of Use

CogFlow was initially developed to give undergraduate students of Psychology an accessible, GUI-forward environment for designing and running their own experiments without first acquiring programming experience. As the platform matured, however, its realistic scope of use grew well beyond that original brief: the same Builder-to-Interpreter pipeline that lowers the barrier to entry for coding-averse novice researchers imposes no corresponding ceiling on complexity, and accommodates custom tasks, paradigms, and hardware and software integrations with little additional friction. CogFlow's intended scope of use is therefore no longer bounded by UX-friendliness for young researchers unfamiliar with stimulus-presentation coding: in current deployment it supports psychophysical, psychological, and cognitive tasks with substantial parameter customisation, spanning both classroom instruction and active multi-investigator lab research, with the platform's role-based permission model (Section 5) allowing both to coexist safely within the same portal. This dual role, as both a low-friction teaching tool and a capable research instrument, reflects on the incidental universality and widening of the scope of use of CogFlow. Section 7.2 outlines how the current development roadmap, including expanded paradigm coverage, GUI-based custom task authoring, and further hardware and software integrations, is intended to widen that scope further without raising the barrier to entry for first-time users. To facilitate user uptake, CogFlow contains a range of tutorials demonstrating many of the platform features described in this paper (see https://cogflow.app/tutorials).

CogFlow's dual role as an educational tool and a research platform is also a point of difference between it and similar existing platforms. As Table 1 shows, it is most common for other platforms to offer one or two elements of the experiment deployment pipeline, but not all three elements of building, analysis, and collaboration. Those platforms that offer more flexibility in design and deployment are also less often free and open-source. The most similar platforms to CogFlow in terms of scope and features are https://labvanced.com which offers the same features but requires a paid plan to access some of them, and https://www.psychopy.org + https://pavlovia.org/ which provides the same deployment and collaboration options, but without equivalent analysis tools. CogFlow allows educators to guide students through each step of the process of gathering and analysing data within a single platform, and enables research teams to complete primary research securely without requiring multiple platforms or knowledge of multiple coding languages. Students can also use the knowledge they gained using CogFlow to transition to more advanced research projects, without the need to relearn technical aspects of the experiment building or analysis process. This places CogFlow in a unique position among equivalent platforms.

7.2 Planned Development

Two complementary lines of development are planned for CogFlow's paradigm library. The first extends the platform's existing continuous-presentation engine, already used for paradigms such as Continuous Image Presentation (CIP) and Security Operations Center Dashboard (SOC-dashboard) scheduling, to support more complex and genuinely multi-task presentation designs, in which several concurrently running subtasks with independent timing and overlapping presentation windows can be composed and scheduled within a single study rather than authored as bespoke, one-off plugins. The second runs in the opposite direction of complexity: expanding the built-in library of classical paradigms (e.g., Posner cueing, Garner interference, Navon global/local task, among others) so that researchers who need a validated, ready-to-use implementation of an established manipulation are not required to rebuild it from primitives, lowering the effort required to include a standard task within a larger study.

A further planned addition is an editable authoring surface for the existing "Custom" task type. At present, bespoke paradigms are added to CogFlow in one of two ways: researchers may develop a jsPsych plugin themselves and contribute it through the GitHub repository, or commission the CogFlow development team to build a task tailored to their experiment. The planned extension is intended for researchers already familiar with jsPsych (de Leeuw et al., 2023) who wish to write plugin-level task logic directly within the Builder's GUI, retaining the platform's configuration versioning, JSON export, and deployment infrastructure for tasks that the built-in library does not yet cover.

Software and hardware integration work is planned on two further fronts. On the data-acquisition side, this includes Lab Streaming Layer (LSL) compatibility with multiple EEG acquisition systems and software products, with possible expansion into other neuroscientific data modalities, building on the pylsl bridge already included in CogFlow To Go (Section 2.6) toward validated, hardware-synchronised data collection. On the curricular side, this includes "out-of-the-box" educational modules built around common course components in university-based Psychology, Cognitive Science, and Neuroscience programmes at both the undergraduate and graduate level, intended to let instructors deploy a validated teaching exercise (for example, a standard demonstration paradigm together with an accompanying analysis walkthrough) without first assembling it themselves in the Builder.
