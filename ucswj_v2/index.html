We found 11 non-significant p values that should be checked for appropriate interpretation.

Show details

Meta-scientific research has shown nonsignificant p values are commonly misinterpreted. It is incorrect to infer that there is ‘no effect’, ‘no difference’, or that groups are ‘the same’ after p > 0.05.

It is possible that there is a true non-zero effect, but that the study did not detect it. Make sure your inference acknowledges that it is possible that there is a non-zero effect. It is correct to include the effect is ‘not significantly’ different, although this just restates that p > 0.05.

How Ethics Approval Check works

This module searches for statements of ethics approval, IRB approval, institutional review board approval, and related terms.

Patterns are designed to capture:

Human research committee names - Institutional Review Board / IRB (US standard) - Independent Ethics Committee / IEC (ICH-GCP international clinical trial term) - Ethical/Ethics Review Board (generic) - Ethics (Advisory/Review) Committee/Board/Panel/Sub-committee - Research Ethics Committee/Board/Panel (UK/Canada/Australia) - Medical Ethics Committee - Human Subjects/Research Committee / Human Research Ethics (Advisory) Panel - Committee for/on the Protection of Human Subjects - Committee on (Health) Research Ethics - Office of Research Ethics - Abbreviations: IEC, REC, REB, ERB, METC, DEC. REC/REB/ERB/DEC are short enough to collide with unrelated jargon (e.g. REC as a recognition-heuristic model abbreviation, DEC as a decision-task label, Reb as an author surname), so these four require an ethics/approval/committee/board/panel/institutional/ protocol word within ~30 characters in the same sentence. IRB and IEC are kept unconstrained as they are not observed to collide in practice. - Dutch: Medisch-ethische toetsingscommissie (METC) - French: Comité d'éthique / Comité d'Ethique

Patterns are NOT designed to capture: - General ethical considerations or ethical dilemmas in study content - Mentions of “ethics” in theoretical or philosophical contexts - Author approval of a manuscript (e.g. “all authors approved the final version”) - Ethical behaviour as a measured variable (e.g. “ethical decision-making”) - URLs containing “ethics” in path components

Live data collection is detected by the internal helper .detect_live_data(), which searches for sentences indicating that data were collected directly from human or animal participants. A paper that states that no human or animal subjects took part (“no human subjects were involved”, “did not involve human participants”, or people taking part “not as subjects”) is not expected to have an ethics statement, whatever participant phrase it also has (see .detect_no_participants()). How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold” or “legend”). Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Codebook Check works

This module checks whether the data columns in a repository are documented in a codebook or README. How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Individual differences in cognitive abilities may influence how people develop and maintain trust in automated systems, yet the mechanisms underlying this relationship remain poorly understood. This study investigated how three foundational cognitive abilities -working memory (WM), attention control (AC), and fluid intelligence (Gf) -shape trust dynamics, particularly focusing on trust decline and recovery after automation failures. Participants (n=111) completed cognitive tests measuring WM, AC, and Gf before performing a dual-task paradigm where they monitored an automated memory aid exhibiting varying reliability levels (100%-65%-100%) while completing a mental arithmetic task. Results revealed that WM and Gf positively predicted trust recovery after automation failures, while AC influenced long-term trust calibration, with high-AC individuals showing more nuanced trust adjustments reflecting system reliability history. Trust decline was uniform across ability levels, suggesting immediacy of trust loss. The relationship between abilities and trust may have been partially mediated by automation schemas, with WM negatively correlating with all-or-none thinking about automation. These findings suggest different cognitive abilities play distinct roles in trust dynamics: WM supports monitoring automation performance, Gf enables effective schema updating, and AC facilitates appropriate deployment of these resources for trust calibration. This work advances our understanding of trust mechanisms and has implications for designing automation interfaces that accommodate individual cognitive differences.

INTRODUCTION

Automation has expanded from specialized domains to everyday life, including vehicles, entertainment, and shopping. While reliable automation can reduce workload and improve performance (Wickens & Dixon, 2007), failures can erode user trust (Lee & Moray, 1994; Lee & See, 2004). Since trust influences automation use (Muir, 1987), recovering it after failures is crucial for continued use.

Trust recovery can be active (trust repair) or passive. While research shows machines can actively repair trust (de Visser et al., 2018; Pak & Rovira, 2023), this may not always be feasible due to practical limitations or because effective trust repair strategies are highly context dependent. Thus, understanding passive trust recovery and its influencing factors is crucial. This study focuses on passive trust recovery rather than active trust repair strategies.

Trust Recovery

Research shows trust tends to recover naturally after automation failure, assuming no subsequent errors. In Lee and Moray's (1992) simulated process-control study, participants supervised automation by allocating functions between automatic and manual control. After an automation failure, trust declined but gradually recovered as the automation resumed reliable performance. Mishler and Chen (2023) observed a similar pattern in a driving simulator.

Participants completed a series of drives in which the automation avoided road hazards successfully, but the system experienced a transient failure midway through the experiment.

Trust dropped after this failure but recovered once the fault disappeared. However, the extent of recovery differed across studies. Whereas Lee and Moray saw trust return to pre-failure levels, Mishler and Chen noted incomplete recovery, suggesting full recovery may require more time.

These studies demonstrate passive trust recovery occurs, but its extent and duration may vary.

The Potential Link Between Cognitive Abilities and Trust: Automation Schema

Cognitive abilities may influence trust by affecting the user's automation schemaknowledge structures organizing related information. Schemas are similar to mental models (Johnson-Laird, 1983) and situation models (Radvansky & Dijkstra, 2007). An updated automation schema likely contributes to more calibrated trust perceptions (de Visser et al., 2020).

However, schema updating is not automatic and depends on cognitive resources (Radvansky & Dijkstra, 2007).

Automation schemas explain operators' trust and reliance on automation. Dzindolet et al. (2002) introduced the Perfect Automation Schema (PAS), showing that users with PAS have high expectations and all-or-none thinking about automation performance. Merritt et al. (2015) later operationalized PAS with a scale measuring these two dimensions. They found that individuals with strong all-or-none beliefs experience greater trust decrease after automation failures compared to those with weak all-or-none thinking. This suggests that users with PAS are less forgiving of automation errors because such errors violate their schema.

These findings support the notion of a cognitive knowledge structure, the schema, that influences users' perceptions of automated systems, and therefore affects trust. Although the cognitive factors that contribute to the building and updating of automation schemas have not been empirically studied, schema updating is known to depend on cognitive abilities such as working memory (Radvansky & Dijkstra, 2007).

Schemas may explain the link between working memory (WM) and trust in automation. Rovira, Pak, and McLaughlin (2017) found that individuals with lower WM had higher trust in automation than those with higher WM, even when automation was not perfectly reliable. . This could be because lower WM individuals lack resources to maintain information about automation performance and update their schemas, leading to inappropriate trust calibration (i.e., under-or over-trust). In contrast, those with higher WM may have spare resources to analyze automation performance and calibrate trust appropriately.

The Current Study

Individuals with low working memory (WM) may struggle to remember and integrate past automation failures into their schema, potentially leading to overtrust compared to those with high WM. This unexplored theory could explain the observed WM-trust link (Rovira et al., 2017). This study specifically examines WM's effect on trust decline and recovery after automation failure, a relationship previously only indirectly implicated (Rovira et al., 2017). To specifically examine the relationship between WM and trust, participants were placed in a situation where the reliability of automation changed abruptly, between blocks. We then examined how individual differences in WM related to trust dynamics as reliability changed.

This study also explores how two cognitive abilities closely linked to WM might influence the results: fluid intelligence (Gf) and attention control (AC). Gf is the capacity to solve novel problems and adapt to new situations (Engle et al., 1999). In the context of trust calibration, Gf may help users recognize patterns in automation performance, interpret what changes in reliability mean, and revise their automation schema when new evidence conflicts with prior expectations. In this way, Gf may support more accurate trust calibration by helping users update their understanding of the automation over time. AC, which researchers also refer to as cognitive control, executive control (Botvinick et al., 2001), or inhibition (Miyake & Friedman, 2012), is the ability to regulate information processing to achieve goal-directed behavior (Burgoyne & Engle, 2000). In the context of trust calibration, AC may help users allocate attention to reliability-relevant automation cues while disengaging from irrelevant information. This attentional regulation may support a more accurate evaluation of automation performance, which may in turn contribute to a more accurate automation schema and bettercalibrated trust. WM, Gf, and AC are related but conceptually distinct abilities. Both Gf and AC have consistently shown strong relationships with WM (Draheim et al., 2022; Pak et al., 2023; Kyllonen & Christal, 1990; Burgoyne & Engle, 2000). Recent research has revealed that AC functions as a higher-level executive system that coordinates the deployment of either Gf or WM based on task requirements (Burgoyne et al., 2023). Specifically, when a task demands information maintenance over time, AC engages WM processes. However, when faced with goal conflicts or distractions, AC activates Gf to resolve these conflicts. Consistent with this view, Draheim et al. (2021) demonstrated that the well-established correlation between WM and Gf becomes non-significant when controlling for individual differences in AC, suggesting that AC mediates the relationship between WM and Gf.

These distinctions are important for understanding trust calibration. WM may support monitoring by helping users keep recent automation successes and failures available. Gf may support schema updating by helping users reason about whether changes in reliability reflect isolated failures or broader changes in automation performance. AC may support trust calibration by regulating attention and helping users apply maintained information and reasoning to reliability-relevant cues. Although existing automation and individual-differences research has primarily focused on WM (e.g., Rovira et al., 2017), the close relationship among WM, Gf, and AC suggests that these abilities may each contribute to automation schemas and, consequently, trust dynamics. Examining all three abilities therefore allows us to test whether trust decline and recovery rely on the same cognitive mechanisms or on distinct components of cognition.

We make two assertions based on prior research; first that abilities affect schema quality (Gilbert & Rogers, 1999; Radvansky & Dijkstra, 2007; Valadao et al., 2015), and second that the schema quality will affect trust (Dzindolet et al., 2002; Merritt et al., 2015; Weis & Wiese, 2022). From these assertions, this study has four hypotheses: • Hypothesis 1: Consistent with Rovira et al. (2017) when automation is reliable, individuals with lower WM will have higher trust than those with higher WM.

• Hypothesis 2: When automation becomes unreliable, individuals with lower WM will show less trust decline than those with higher WM. Individuals with lower WM will not be able to obtain an accurate automation schema of the automation's past performance (because they will be less able to remember all the failure instances). Contrarily, those with higher WM will be able to remember the failures and form a better automation schema.

• Hypothesis 3: When automation is set back at 100% reliability, individuals with lower WM will show greater trust recovery than those with higher WM because they are less likely to notice and remember the past failures from Block 2.

• Hypothesis 4: Given the close relationship between WM, AC, and Gf (Draheim et al., 2022; Pak et al., 2023), those with higher AC and Gf may generally have better trust calibration (trust decline and recovery will be more responsive to automation reliability) than those with lower AC and Gf. Given the exploratory nature of these variables, we do not make specific predictions with regard to Gf or AC's unique role.

METHOD Participants

Two hundred and one participants attempted the study. After those with random computer issues due to the online nature of the study were removed, 144 remained. These were later filtered down to a final sample of 111, as detailed in the Data Preparation section of the Results. This research complied with the American Psychological Association Code of Ethics and was approved by the Institutional Review Board at Clemson University.

Materials

Ability tests. Three cognitive abilities -working memory (WM), attention control (AC), and fluid intelligence (Gf) -as well as automation schema and trust, were assessed. WM was measured using shortened operation span (Kane et al., 2004; Turner & Engle, 1989) and symmetry span (Unsworth et al., 2009). AC was measured using the three "squared" tests (Burgoyne et al., 2023; Pak et al., 2023). Gf was measured using Raven's advanced progressive matrices (Kane et al., 2004; Raven et al., 1998) and number series (Unsworth et al., 2009; Thurstone, 1938). Automation schema was measured with the PAS scale (Merritt et al., 2015), which consists of two dimensions (high expectations of automation and all-or-none thinking).

All cognitive tests and PAS scale were administered prior to the experimental task.

Experimental Task. The task was a web-based synthetic work paradigm modeled on SynWin (Elsmore, 1994). Synthetic work paradigms allow the study of multitasking and complex task performance in the laboratory without strongly resembling a specific task or domain and thus do not require extensive task-specific training (e.g., Barron & Rose, 2017; Redick et al., 2016). In our adaptation, called SimWork (Mashburn et al., 2024) two simultaneous subtasks (i.e., memory and arithmetic tasks) were presented to the participant (Figure 1).

The first subtask was a Sternberg memory probe where six randomly selected letters were shown for 5 seconds and then disappeared. A random probe letter appeared in the center of the subtask every 5 to 6 seconds. The task was to determine whether the probe letter was in the original memory set. The type of automation was consistent with Parasuraman, Sheridan, and Wickens' (2000) stage 4 automation (action automation). In the training session, the participant was responsible for carrying out both tasks with no automation assistance. observable while the arithmetic task was completely manual. If the memory automation (left) performed the task successfully, a message 'Correct!' was shown next to the answer. However, if the automation failed, a message 'Incorrect!' was shown instead. The memory task and memory automation's actions and performance were completely observable at all times. Participants' primary task was the arithmetic task. Scores for each subtask were shown at the top right corner of the subtask, and the combined score was presented at the bottom.

The second subtask was an arithmetic task where participants either added or multiplied two sets of numbers. In the low workload condition, the participant's task was to add two 2-digit numbers. In the high workload condition, participants multiplied a 1-and 2-digit number (see Figure 2).

Design and Procedure

This between-subjects experiment randomly assigned participants to low or high workload conditions. Participants were informed they were collaborating with automation on a task, and that they should try to maximize their combined score. They completed three 5-minute blocks, each containing about 33 automation trials. Before the experimental blocks, participants underwent a 6-minute training session (three 2-minute blocks) where they performed subtasks manually and simultaneously (Figure 3).

Participants completed three experimental blocks with automated memory tasks and manual arithmetic tasks. Automation reliability was manipulated across blocks and refers to the proportion of trials in which the automated aid produced the correct response. The first and third blocks had 100% automation reliability, while the second block had 65% reliability (about 12 errors in about 33 trials). Block 2 was therefore the failure block, whereas Blocks 1 and 3 represented perfectly reliable automation before and after the failure period. Sixty-five percent reliability was chosen because it falls below the approximate 70% threshold at which imperfect automation may become more harmful than helpful. Prior work suggests that below this level, human-automation performance can be worse than unaided performance, and trust tends to decline rapidly (Lee & See, 2004; Wickens & Dixon, 2007). Thus, the 65% reliability block was intended to create a clearly unreliable automation period that would produce a measurable decline in trust while still allowing trust recovery to be examined once automation returned to 100% reliability. Errors were either incorrect responses or offline status, equally distributed. An automation status window provided real-time feedback, with color-coded responses indicating correctness. Participants could only observe the memory subtask and automation activity without intervention, ensuring consistent exposure to reliability levels across participants. This design was chosen to focus on trust in automation rather than reliance behaviors.

At the end of each block, participants were asked to evaluate their level of trust in the memory task aid using the question, "How much did you trust this automated memory aid?"

Responses were recorded on a visual analog scale ranging from 1 (not at all) to 10 (extremely).

In this study, trust decline and trust recovery were operationalized using these self-reported trust ratings. Trust decline refers to the change in trust ratings from Block 1, when the automation was 100% reliable, to Block 2, when reliability decreased to 65%. Trust recovery refers to the change in trust ratings from Block 2 to Block 3, when automation reliability returned to 100%. A singleitem trust measure was used based on findings by Patton and Wickens (2024), which demonstrated that it correlates more strongly with trusting behavior (e.g., dependence) compared to multi-item trust measures (e.g., Jian, Bisantz, and Drury, 2000). Furthermore, research employing multi-item trust measures has shown that the results of other items (e.g., predictability and dependability) closely align with those of the trust item (Lee & Moray, 1992). These findings indicate that a single-item trust measure is as effective as multi-item measures in assessing trust.

DISCUSSION

The primary goal of our study was to investigate the influence of WM on trust as previous research identified its connection to trust in automation (Rovira et al., 2017). We hypothesized that the creation and updating of a cognitive knowledge structure (automation schema) is dependent on WM and other abilities (Gilbert & Rogers, 1999; Radvansky & Dijkstra, 2007; Valadao et al., 2015), and this automation schema influences trust (Dzindolet et al., 2002; Merritt et al., 2015; Weis & Wiese, 2022). The pattern of correlations between WM, automation schema, and trust is consistent with this hypothesized mechanism linking abilities to trust.

We also included measures of AC and Gf, which are known to be associated with WM, for exploratory purposes. To our surprise, these additional cognitive variables yielded unexpected findings. No abilities predicted the decline of trust, and trust recovery was predicted by WM and Gf. Finally, the extent to which trust fully recovered to pre-failure levels (trust change) was related to WM and AC. Our general exploratory hypothesis that AC and Gf would play a role in trust dynamics was supported (hypothesis 4).

We expected to replicate prior research showing a negative relationship between WM and trust (Rovira et al., 2017), but our findings differed. WM was not correlated with trust after exposure to 100% reliable automation (block 1). However, WM and Gf were positively correlated to trust at the study's end, after experiencing varying reliability levels. Two questions arise: Why wasn't WM correlated to trust after the first block? And why might it be positively correlated, instead of negative as Rovira et al. demonstrated? Methodological differences may explain these discrepancies. Rovira et al. measured trust after exposure to 80% reliable automation, while our initial trust was measured after 100% reliable automation (block 1). With no failures in the first block, there was no need to remember past failures to update an automation schema, thus no relationship with WM. After experiencing different reliabilities, participants may have needed to remember and integrate/update their automation schema, requiring WM and Gf. Moreover, our automation was only observable, while in Rovira et al., it assisted in the primary task. Automation that actively assists necessarily draws more user attention to its behavior, potentially affecting the relationship between WM and trust.

The positive relationship between working memory (WM) and trust in our study, contrasting with Rovira et al.'s findings, may again be due to methodological differences. We used two complex span tasks to measure WM, potentially better isolating the construct compared Our results align with prior literature showing that trust decreases when automation reliability decreases (Lee & Moray, 1992; Mishler & Chen, 2023). However, contrary to our hypothesis, cognitive variables (WM, AC, Gf) were not associated with trust decline, suggesting this process may not be resource-limited in our study (Norman & Bobrow, 1975). The 65% reliability in our failure block, chosen based on reviews by Wickens and Dixon (2007) and Lee and See (2004), may have been so low that it was very salient. It is possible that clearly visible automation failures triggered affective processing (feeling-based) rather than analytic processing (evaluation-based), which is more cognitively demanding (Lee & See, 2004). When failures are this noticeable, users may respond with an immediate decline in trust that operates independently of higher-level cognitive resources. This may explain why the decline in trust appeared relatively uniform across individuals who differed substantially in cognitive abilities.

Contrary to our hypothesis, we found WM and Gf were positively related to trust recovery. This may be because individuals with higher WM can better remember recent automation performance while multitasking. Those with higher Gf may more effectively integrate or update their automation schema with new performance information, guiding their trust ratings. When errors cease, high Gf individuals may be better at updating their schema by discarding old information and incorporating new data. In essence, WM may be crucial for monitoring automation performance, while Gf may be key for updating the automation schema.

The absence of a relationship between trust recovery and AC suggests that recovery doesn't require flexible deployment of WM and Gf, but rather relies on both abilities simultaneously.

Our results show that trust change from initial exposure to block 3 was related to WM and, to a lesser extent, AC. Participants with higher WM demonstrated nearly full trust recovery (flat trust slope), while those with lower WM did not (negative trust slope). This suggests that higher WM individuals may have more responsive trust calibration, with their trust ratings closely matching the actual reliability of the automation. Lower WM individuals' trust at block 3 remained lower than at block 1, indicating less responsive calibration. One factor that may contribute to this difference is relationship between WM and automation schema. We found that all-or-none thinking was negatively related to WM. Higher WM individuals were less likely to believe automations are completely useless after errors. In contrast, lower WM individuals might have perceived the automation as broken after failures in block 2, leading to a permanent decrease in trust at block 3, even after errors were corrected.

Individuals with high AC lowered their trust at study's end, while low AC showed no change. This counterintuitive finding may represent optimal trust calibration; high AC individuals likely incorporated the variable reliability (100%, ~65%, 100%) into their schema.

Consequently, their trust should be lower than after experiencing only 100% reliability (block 1).

Low AC individuals showed no trust changes between blocks 1 and 3, suggesting their ratings were based primarily on recent information. They may have struggled to disengage from less relevant data (block 2's momentary reliability change, Gf-dependent) and to recall block 1 performance (WM-dependent) when forming an updated schema. These results may illustrate the two types of trust calibration: short-term and long-term. Short-term calibration (i.e., swift trust; Capiola et al., 2020; Meyerson et al., 1996) is trust from immediate experiences while long-term calibration (de Visser et al., 2020) incorporates both recent and historical performance.

WM might assist with moment-by-moment, short-term trust calibration, while AC may aid accurate long-term calibration by recalling past performance (WM) and updating the automation schema (Gf).

DESIGN IMPLICATIONS FOR TRUST-CALIBRATED INTERFACES

Our findings suggest that appropriate trust calibration depends on cognitive resources that vary across individuals. This has direct implications for automation interface design, particularly for systems where trust recovery and long-term calibration are critical for safe and effective use.

Rather than designing interfaces that present performance information uniformly to all users, systems could benefit from adaptive or flexible displays that accommodate different cognitive profiles.

Our results point to three broad principles that may inform future interface design. First, users with lower WM may benefit from explicit memory support through performance summaries and visual trend displays, reducing the cognitive burden of tracking automation behavior over time. This is suggested by our finding that WM predicts trust recovery, which implies that high-WM individuals may be able to track recent performance internally while low-WM individuals may struggle to do so. Second, AC influences how users weigh historical versus recent information, implying that interfaces should make both types of information available but may need to emphasize them differently for different users. High-AC users benefit from comprehensive historical context that supports nuanced long-term calibration, while low-AC users may need recent performance emphasized to avoid over-weighting outdated information.

Third, given Gf's role in schema updating, explicit explanations of reliability changes can assist users (particularly those with lower Gf) in appropriately revising their understanding when system performance shifts.

LIMITATIONS

There are several limitations that warrant more follow-up research. First, participants could not intervene in the automated task, which may reduce their motivation to monitor automation performance and therefore influence trust. To address this concern, we emphasized that participants' final score depended on both their own performance and the automation's performance. This instruction encouraged participants to remain aware of the automation's reliability, and the observed trust changes across blocks confirm that they were indeed monitoring its performance. Second, because the purpose of the research was to examine the relationship between abilities and trust change, we used a simplified task that was automated but was not tied to a specific domain or required specialized training. While this may enhance generalizability of the results, it ignores task-specific factors that may influence trust such as risk, or domain (Pak et al., 2017). For example, Highland et al. (2023) showed that, in combat aviation, trust in autonomy depends on automation performance as well as perceived risk, workload, and the consequences of undertrust or overtrust. Thus, trust decline and recovery may operate differently when automation failures carry more serious consequences. Relatedly, the participants in our study were mostly college-aged students which reduced the generalizability to other populations. Third, we hypothesized that any influence of cognitive abilities on trust was mediated by the automation schema that was dependent on various abilities (e.g., Radvansky & Dijkstra, 2007) which would then affect trust (e.g., Merritt et al., 2015). However, we only measured the automation schema once and did not measure if it may have changed with exposure to automation. In addition, we only measured one conception of the automation schema (perfect automation schema) which may only represent one kind of information contained in the user's knowledge structure. Future research should explore more direct measurements of the schema (e.g., what information is contained in it), and assess it more frequently to definitely implicate the role of abilities in trust.

CONCLUSION

These results provide some insight into trust dynamics; namely that losing trust is easy (i.e., is independent of cognitive resources) but recovering trust is hard (i.e., it requires several abilities). The notion that trust recovery is resource-constrained is consistent with recent theories of trust repair that suggest that the efficacy of active trust repair may be dependent on cognitive resources (Pak & Rovira, 2023). The resource constraint may come from the need to update the knowledge structure (automation schema), which is likely effortful (i.e., requires cognitive resources; Chen, 2002). It also gives an explanation for the age-related differences in trust recovery that have been previously observed (e.g., Sanchez et al., 2014). Age-related declines in a wide range of fluid abilities (McLaughlin & Pak, 2020) may make the trust recovery process slower or less responsive. Effective trust calibration requires cognitive processes that vary across individuals, which highlights the need for automation designs that provide customizable and cognitively supportive features. Such features can guide attention, support memory and reasoning, thereby helping users maintain appropriate trust, especially in multitasking or highworkload environments. Current trust calibration interventions focusing on working memory (e.g., McGuirl & Sarter, 2006; Price et al., 2016) should be complemented with methods to enhance attention control and reasoning. This could lead to more accurate automation schemas and better trust calibration. For instance, ecological display design approaches (e.g., Skraaning & Jamieson, 2021) may reduce comprehension effort while improving automation schemas and trust calibration. Overall, this study extends trust in automation research by showing that passive trust recovery is shaped not only by automation reliability, but also by the cognitive abilities users bring to the interaction.
