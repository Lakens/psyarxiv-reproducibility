Files that do not belong in the repository

We left out 17 files that software creates by itself, not the authors: operating system (16), R history (1). They hold nothing a reader can use, but they clutter the repository, and software can mistake them for real files (for example a ._ copy of a .csv for data).

Remove these: Operating system files: macOS adds a __MACOSX folder and a ._ copy of every file it puts in a zip, and .DS_Store files to folders; Windows adds Thumbs.db and desktop.ini. On a Mac, create zips from the command line with zip -r -X, or remove them afterwards with zip -d archive.zip "__MACOSX/*" "*.DS_Store". RStudio session files (.Rproj.user/) hold open tabs and unsaved edits; R history (.Rhistory) lists the commands typed in a session and can hold file paths and passwords; Jupyter checkpoints (.ipynb_checkpoints/) are automatic copies of notebooks; compiled Python files (__pycache__/, .pyc) are recreated when the code runs; open-document lock files (~$...docx, .~lock...#) are left while a document is open; editor backups (file~, .bak, .swp) and temporary files (.tmp, .temp) are copies a program made by itself.

Keep only on purpose: version control folders (.git, .svn, .hg) hold the project’s history, which can include earlier versions of files and data that was later removed; editor settings (.idea, .vscode) can hold paths on your own computer. A .gitignore based on GitHub’s templates (https://github.com/github/gitignore) keeps them out of a repository.

To improve Non-Significant P Value Check

What we found

We found 21 non-significant p values that should be checked for appropriate interpretation.

Show details

Meta-scientific research has shown nonsignificant p values are commonly misinterpreted. It is incorrect to infer that there is ‘no effect’, ‘no difference’, or that groups are ‘the same’ after p > 0.05.

It is possible that there is a true non-zero effect, but that the study did not detect it. Make sure your inference acknowledges that it is possible that there is a non-zero effect. It is correct to include the effect is ‘not significantly’ different, although this just restates that p > 0.05.

All participants provided informed consent/assent prior to participating and were compensated with $20/hour (CAD) and a performance-dependent bonus up to $3.

To learn the overlapping pairs, participants completed eight cycles of alternating study and test (Fig. 1b).

During study, each pair was presented for 3.5 seconds (0.5s inter-trial interval [ITI]) and participants were instructed to think of a story linking the items.

After study, participants were tested on their memory with feedback.

Participants were informed of and practiced both neutral and specific question types prior to learning.

To assess how overlap influenced memory for shared and unique features, participants completed a self-paced, post-training memory test (0.5s ITI) with questions following three structures: neutral, specific, or general (Fig. 1c).

At the end of the experimental session, participants completed a task in which they visually discriminated between exemplars from high and low overlap categories.

We reasoned that if participants were similarly accurate in discriminating high and low overlap items, this would indicate that any effects of pair overlap on memory did not appear merely because participants were less accurate in identifying items from high compared to low overlap categories as different from one another.

A main effect of trial type in this model is akin to corrected hit rate in that it reflects to what degree participants are more likely to respond “different” for items that are actually different compared to those that are the same.

Participants were more likely to remember the correct object-artifact pairings as training progressed (Fig. S1a; quadratic effect of training cycle for neutral: b=-18.27, 95% CI [-31.10, -5.43], z=-2.79, p=.005 [quadratic predictor improved model fit: c 2 (15)=27.91, p=.02]; linear effect for specific: b=0.50, 95% CI [0.34, 0.65], z=6.32, p<.001 [quadratic predictor did not improve fit: c 2 (15)=8.34, p=.9]) and adults were more accurate compared to adolescents (neutral: b=0.38, 95% CI [0.12, 0.64], z=2.82, p=.005; specific: b=0.28, 95% CI [.04, 0.52], z=2.28, p=.02).

Participants were also less accurate on high compared to low overlap pairs through both initial neutral (b=0.46, 95% CI [0.31, 0.61], z=6.00, p<.001) and later specific (b=0.92, 95% CI [0.74, 1.10], z=9.97, p<.001; no significant two-or three-way interactions among overlap, cycle, and age group for neutral [all z<1.9, p>.06] or specific [all z<1.0, p>.3]) cycles.

Considering response times on correct trials revealed similar effects (Fig. S1b; Supplementary Results), and additionally indicated that (1) adults sped up over specific training at a steeper rate than adolescents and (2) participants were particularly slowed by the transition to specific questions for high compared to low overlap pairs.

Collapsed across age groups, we found that the effect of overlap differed by question type (question x overlap interaction: b=0.51, 95% CI [0.28, 0.75], z=4.33, p<.001; question: b=0.15, 95% CI [-.09, 0.38], z=1.21, p=.2; overlap: b=0.18, 95% CI [-.06, 0.41], z=1.49, p=.1) in an intuitive pattern: Participants were less likely to remember the specific exemplar (z=-3.79, p<.001) but more likely to remember the correct category (z=2.21, p=.03) for high compared to low overlap pairs.

Within this model, we first confirmed that participants completed the task correctly: Exemplars from the same category were indeed reliably discriminated from one another (correctly identified as “different” more often than identical items: b=3.02, 95% CI [3.21, 2.84], z=32.18, p<.001) by both adults (z=23.46, p<.001) and adolescents (z=22.26, p<.001).

Our overlap manipulation also had the expected effect on response times for both adolescents and adults (Fig. 3c): Participants were slower to correctly discriminate high compared to low overlap exemplars (b=.01, 95% CI [.02, .007], t(318.94)=-3.79, p<.001) with no reliable difference across age groups (age group x overlap interaction: b=.003, 95% CI [-.005, .01], t(318.94)=0.67, p=.5; adolescents slower than adults overall: b=.08, 95% CI [.02, 0.14], t(71.00)=2.63, p=.01).

Interestingly, participants were never explicitly prompted to integrate and if anything, task instructions and cycles of specific-level training encouraged participants to distinguish between related pairs (Hulbert & Norman, 2015).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

How PubPeer Comments works

This module checks references and warns for citations that have comments on pubpeer (excluding Statcheck comments).

The PubPeer module uses the PubPeer API to check for each reference that has a DOI whether there are comments on the post-publication peer review platform. If comments are found, a link to the comments is provided. Comments by ‘Statcheck’ on PubPeer are ignored, see https://retractionwatch.com/2016/09/02/heres-why-more-than-50000-psychology-studies-are-about-to-have-pubpeer-entries/.

The module requires that the reference has a DOI. If you run the doi_check module in a pipeline before this, it will use the enhanced DOI list from that module, otherwise it will only run on references with existing DOIs.

For more information, see PubPeer.

How RetractionWatch works

This module checks references and warns for citations in the RetractionWatch Database.

The RetractionWatch Check module compares the reference list against studies in the RetractionWatch database based on the DOI. If a study in the database is found, a reminder is provided that the study was retracted, has an expression of concern, or a correction.

The module requires that the reference has a DOI. If you run the ref_doi_check module in a pipeline before this, it will use the enhanced DOI list from that module, otherwise it will only run on references with existing DOIs.

It is possible the authors are already aware that a study was retracted, but the module can’t evaluate this.

The database can be manually updated with the rw_update function. For more information, see https://gitlab.com/crossref/retraction-watch-data.

How Replication Check works

This module checks references and warns for citations of original studies for which replication or reproduction studies exist in the FLoRA database.

The Replication Check module compares the reference list against studies in the FLoRA (FORRT Library of Replication Attempts) database based on the DOI. If a study in the database is found, a reminder is provided that a replication or reproduction of the original study exists, and should be cited (currently, a warning is provided regardless of whether the replication/reproduction study is already cited).

The module requires that the reference has a DOI. If you run the ref_doi_check module in a pipeline before this, it will use the enhanced DOI list from that module, otherwise it will only run on references with existing DOIs.

It is possible the original study was cited for other reasons than the empirical claim tested, or that the replication/reproduction in the FLoRA database is for only one of the studies in the paper, and not the study the authors discuss.

The database can be manually updated with the FLoRA_update() function. For more information, see https://forrt.org/FLoRA/.
