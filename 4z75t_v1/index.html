How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold” or “legend”). Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Webcam eye tracking allows researchers to study eye movements in large, geographically diverse online samples, but its accuracy has limited it to coarse comparisons, such as which half or quadrant of the screen a participant is looking at. We introduce SaccadeJS, an open-source webcam eye tracker that runs entirely in the participant's browser. SaccadeJS uses a neural network to transform images of the eyes to features, which a ridge regression maps to screen positions. The network can be rapidly calibrated by computing new regression weights on a sample of fixations at known locations. To train the model, we collected a new dataset of 2,003 participants who fixated targets on their own laptop and desktop computers. In a validation study with 200 new online participants, the median participant's error was about 4% of the screen diagonal. That accuracy is enough to distinguish many more, and smaller, areas of interest than halves and quadrants. We also developed a timing calibration routine to measure each participant's camera lag. After correction, saccade latencies matched distributions from laboratory experiments. We report how different calibration strategies and image characteristics affect accuracy. SaccadeJS could be run in real time on about one third of the participants in the validation study; for others, the library processes frames in the background while the experiment runs. SaccadeJS can be used as standalone software for webcam eye tracking or in conjunction with jsPsych through a set of provided plugins for calibration, validation, and recording.

1 Introduction

What researchers can discover from eye movements has always depended, in part, on the accuracy and precision of the technology used to measure gaze. Long before Yarbus (1967) famously suctioned mirrors to the eyes and recorded scan paths on photosensitive paper, researchers used a variety of creative approaches to measure eye movements (Wade, 2015). Each method revealed different pieces of the puzzle. One striking example is the late 19th century technique of listening to the muscles around the eyes through rubber tubes held against the eyelids (Hering, 1879; Lamare, 1892). The bursts of sound heard during reading revealed that the eyes move along a line of text in a series of jerks rather than a smooth glide, and allowed researchers to count how many jerks each line required, but not where the eyes stopped (Wade & Tatler, 2009).

Today we have eye tracking technology that can seemingly do it all. Specialty hardware systems can record eye movements upwards of 1,000 times per second, with spatial accuracy of about 0.5° of visual angle and precise temporal synchronization (Ehinger et al., 2019; Nyström et al., 2025; SR Research, n.d.). Despite their general availability, these systems are often cost prohibitive (Funke et al., 2016; Nyström et al., 2025), so researchers still use a variety of methods. At the other extreme, the so-called "poor man's eye tracking" (Slim et al., 2024; Trueswell, 2008) relies on researchers watching videos and recording the direction of gaze, and is often deployed in developmental research (Fernald et al., 2008) where calibrating an eye tracker can be challenging (Aslin, 2012; Dalrymple et al., 2018; Hessels & Hooge, 2019). This works well when the only information needed is whether a participant is looking left or right, and has practical advantages like the simplicity of setup.

Laboratory eye trackers do suffer from a major limitation: they are in a laboratory. Participants must travel to the lab, limiting the geographic reach to people nearby. This can lead to an overreliance on convenience samples of university students (Arnett, 2008; Hanel & Vione, 2016; Henrich et al., 2010; Thalmayer et al., 2021), and presents a significant barrier for studying populations where coming into an unfamiliar setting is challenging (Malow et al., 2021; Rhodes et al., 2020; Sheskin et al., 2020). Online experiments offer an alternative, with their own set of tradeoffs. Participation happens in familiar settings with flexible scheduling, many participants can take part simultaneously, and the geographic reach is anywhere with an internet connection (Hartshorne et al., 2019; Rodd, 2024), though online samples remain far from representative (Thalmayer et al., 2021).

Online experiments are now a routine part of behavioral research, and eye tracking has made the leap as well. Webcams are a standard component in consumer laptops, tablets, and phones, and these forward-facing cameras can be used to record the eyes of the viewer. In some ways, this technique is not so different from the methods of the 20th century that involved filming the eye (Buswell, 1935; Judd et al., 1905). However, advances in computer vision have changed what is possible: we can automatically convert photos and videos into predictions about gaze location. iCatcher+, for example, classifies the gaze of infants and young children as left, right, or away from the screen, agreeing with human coders on 85-95% of video frames (Erel et al., 2023). WebGazer (Papoutsaki et al., 2016) estimates where a participant is looking on the screen, with accuracy sufficient to replicate effects that depend on which half or quadrant of a screen a participant is looking at (James et al., 2025; Semmelmann & Weigelt, 2018; Slim & Hartsuiker, 2023; Yang & Krajbich, 2021). Sampling rate and timing accuracy are also worse than laboratory hardware. Webcams capture 10-60 frames per second, the delay between when a frame is captured and when it is timestamped is unknown and varies across machines, and the tracking algorithm takes time to run. As a result, effects measured with WebGazer emerge roughly 200 ms later than the same effects measured in the lab (Slim et al., 2024; Slim & Hartsuiker, 2023).

Advances in computer vision have shown that webcams can do better. State-of-the-art gaze-estimation models, trained on large datasets of images, can estimate gaze to within 2-4° of visual angle on standard benchmarks (Cheng et al., 2024). FAZE, for example, adapts a network trained on many people to a new person from as few as three calibration images, reaching 3.18° on the GazeCapture dataset (Park et al., 2019). When Saxena et al. (2024) ran FAZE on webcam videos that participants recorded at home, its median error was 2.44°. However, these models are research prototypes that are not built for ease of use. To run FAZE, Saxena et al. (2024) recorded and uploaded each participant's webcam video, then processed it offline. Some companies are offering webcam-based tools that are designed for researcher use, including Tobii (Tobii, 2026), RealEye (RealEye, 2026), and Labvanced (Kaduk et al., 2024). These tools appear to be as accurate as the research models, but they are closed-source. Their published validations are mostly run by the companies themselves, often in the lab rather than in participants' homes (Kaduk et al., 2024; Tobii, 2026). These tools are also expensive, with licensing agreements that cost thousands of dollars per year (Labvanced, 2026; RealEye, 2026).

More accurate, easily deployable webcam eye tracking is now possible, in part, because consumer hardware is evolving. WebGazer was built a decade ago to run on a CPU, fitting a linear ridge regression to the pixels of eye images. The 240-parameter model is fit to each participant individually (Papoutsaki et al., 2016). Modern browsers can access a device's GPU hardware for more than graphics processing (World Wide Web Consortium, 2026), allowing neural-network models with millions of parameters to run quickly. Consumer laptops and tablets are now being manufactured with chips that are dedicated to neural-network style computation (Apple, 2020; Mehdi, 2024). A model far larger than WebGazer's can now run in a participant's web browser: in real time on machines with a capable GPU, and in the background on slower ones.

Faster hardware is only one ingredient toward improved eye tracking for online experiments. A second is training data that is representative of the eye movements in these kinds of experiments. Existing gaze datasets match the properties of online research environments in some respects but not others (Table 1). Several were recorded in the lab, often with multiple cameras or specialized ones (Fischer et al., 2018; Funes Mora et al., 2014); some used a chin rest or head rest in order to vary head pose and gaze direction systematically (Smith et al., 2013; Sugano et al., 2014; Zhang et al., 2020); some sample gaze locations that are more dispersed than those that appear on a screen (Fischer et al., 2018; Kellnhofer et al., 2019; Zhang et al., 2020). GazeCapture, by far the largest, was crowdsourced from more than 1,400 people in everyday settings, but on phones and tablets rather than laptops or desktops, which results in a different geometry between the camera, screen, and eyes (Krafka et al., 2016). The datasets recorded at laptop or desktop viewing distances include at most 54 participants, and only two of them were recorded outside of the lab (Evdokimov et al., 2024; Zhang et al., 2015; 2019). Webcam gaze estimation is sensitive to variation in participants' appearance, lighting, reflections, and hardware (Saxena et al., 2024), so a model trained on lab recordings, on phones, or on a few dozen people may not generalize to the range of people and setups in an online study. The lack of representative data also affects systematic evaluation. Models are evaluated with different data distributions, protocols, and metrics, making accuracy in real-world deployment hard to compare.

In this paper we present SaccadeJS, an open-source webcam eye tracker that runs entirely in the participant's browser. Its gaze model is a neural network trained on an original dataset of gaze recordings from 2,003 participants, recorded remotely through their own webcams on laptop and desktop screens. In a validation study with online participants, in which SaccadeJS and WebGazer tracked the same sessions, SaccadeJS roughly halved WebGazer's error (Section 6). That is enough to move online eye tracking beyond halves and quadrants: across the range of participants, SaccadeJS can tell apart many more, and smaller, areas of interest than WebGazer.

Alongside the model, we release several resources for researchers. The dataset is openly available, and its held-out participants, recorded separately from the training set, give other webcam gaze models a common set to compare on (Section 4). A timing calibration routine measures each participant's combined display and camera lag and corrects gaze timestamps for it (Section 5.1). The validation study shows how much calibration a study needs (Section 6.4.2) and what hardware SaccadeJS needs to run in real time, and the library includes a deferred mode for slower machines. Finally, a set of jsPsych1 plugins lets researchers add SaccadeJS to an online experiment with about a dozen lines of code. In the rest of the paper we describe the dataset, the model and its evaluation, how the model runs in the browser, and the validation study.

2.1 Method

Both data-collection tasks can be tried in a browser at https://jspsych.github.io/saccadejs-demos/, as participants ran them but without saving any data. The protocol was approved (as exempt) by the Vassar College Institutional Review Board.

2.1.1 Participants

We recruited participants on Prolific. 1,974 participants completed the first version of the task to generate our training dataset. The held-out dataset came from a second, longer version of the task, with 307 participants. Of those who completed the task, 1,746 and 257 are in the public dataset (see Section 2.3).

Both studies were open only to Prolific participants on a laptop or desktop computer who said they had a webcam they were willing to use and were willing to record themselves on video, and who had an approval rate of at least 98% over at least 20 previous submissions. There was no restriction on country or language. The study description asked participants to use an up-to-date version of Chrome, Edge, or Firefox. The evaluation study excluded everyone who had taken part in the training study, so no one is in both datasets. We asked participants if they were using an integrated webcam (like those at the top of laptop screens) or an external camera. Most participants reported using their computer's integrated webcam: 84% of the training set and 90% of the held-out set. We also asked participants if they were wearing glasses. 24% of the training set and 11% of the held-out set wore glasses during the task.

The training participants were 35.9 years old on average (SD = 12.6, range 18-85) and the held-out participants 32.7 (SD = 10.5, range 18-65). 40% of the training set and 58% of the held-out set were female. Most training participants lived in the United Kingdom (30%), the United States (21%) or South Africa (14%), and most held-out participants in South Africa (54%). In Prolific's ethnicity categories, the training set was 65% White, 17% Black, 7% mixed, 6% Asian and 3% other, and the held-out set 22% White, 66% Black, 6% mixed, 4% Asian and 1% other.

2.1.2 Task

Participants in the training dataset completed a series of 144 trials; participants in the held-out dataset completed 288. During each trial, a fixation target appeared at one of 144 possible locations on the screen (Figure 1). We told participants to "keep your gaze locked onto the dot" and "remain focused on the dot. " On most trials, the dot was visible for 1,500 ms. On 30 of the 144 trials (or 60 of the 288), the ring around the dot changed to red and the center changed to black after the initial 1,500 ms. The participant's task was to press the spacebar as quickly as possible during these trials. The experiment did not advance to the next trial until the participant pressed the spacebar. There were three blocks of trials, allowing a short rest between each group of 48. The 30 detection trials were split evenly over the three blocks. The task began with three practice trials, one of which required a keypress, and the experiment ran in full screen mode. Before completing the fixation task, we gave participants instructions to try and improve the quality of the data. We said: "Please adjust the camera, your position, and the lighting to get a good view of your face and especially your eyes. Here are some tips: (1) To avoid backlighting, make sure a strong light is in front of you. (2) If you wear glasses, try to reduce glare on the lenses as much as possible. (3) You should be the only face in frame. If you can clearly see the whites of your eyes, you're likely in a good spot!"

2.2 Data

During the task, we recorded individual video clips of each trial. The recording started after the first 1,000 ms of the trial, allowing plenty of time for the participant to saccade to the new location of the dot, and lasted for 500 ms. We also recorded the response times to the dot detection task. The number of frames recorded in each video was constrained by the frame rate of the participant's webcam. Averaged over each participant's clips, it ranged from 1.4 to 72.7 frames, with a median of 15.2. Many clips were longer than 500 ms, likely due to unavoidable browser delays. The median participant's clips lasted 592 ms in the training set and 760 ms in the held-out set, and 45% and 75% of participants had a median clip longer than 600 ms. The longest clips came from the slowest cameras: held-out participants recording at 12 frames per second or fewer had a median clip of 978 ms. We asked the browser for video 480 pixels wide, but this was a preference rather than a requirement, and the browser used the nearest size the camera offered: 640 × 480 for 93% of the training set and 93% of the held-out set. The rest ranged from 424 to 2,880 pixels wide, and 17 participants recorded in portrait. Each clip was saved as a WebM file, compressed with the codec the participant's browser chose: H.264 for 80% of the training set and 85% of the held-out set, and VP8 for the rest.

The released dataset includes these raw .webm files and preprocessed image frames that were used for training the model. To generate the model input, we decoded every frame of each video and ran MediaPipe Face Mesh (Kartynnik et al., 2019) on each frame independently, with the refined eye and iris landmarks (Grishchenko et al., 2020), which gives 478 landmarks for the face. If a face was detected, we cropped one rectangle holding both eyes. Its left and right sides are the landmarks just outside the outer corner of each eye (IDs 226 and 446 in MediaPipe's mesh); its top is the higher of the two landmarks just above the upper eyelids (IDs 27 and 257), and its bottom the lower of the two just below the lower eyelids (IDs 23 and 253). The rectangle is never rotated: when the head is tilted, it grows to hold both eyes. Each side was padded by 1% of the frame's width or height. We then converted these cropped images to grayscale, resized them to 144 × 36 pixels whatever their aspect ratio, and adjusted the contrast with contrast-limited adaptive histogram equalization (CLAHE) (Zuiderveld, 1994). CLAHE equalizes the brightness separately within each tile of an 8 × 8 grid, so that a shadow on one side of the face does not alter the contrast for the other. Each frame's record holds this 144 × 36 image, the 478 landmarks, the same crop in color at the camera's resolution before equalization, a 160 × 120 copy of the whole frame, the target's position, and measures of quality: whether a face was found, the crop's sharpness and brightness, and each eye's aspect ratio.

3 The SaccadeJS Gaze Model

Our approach for gaze prediction is inspired by WebGazer (Papoutsaki et al., 2016). Each frame in WebGazer is reduced to two 10 × 6 pixel grayscale images, one for each eye, which are flattened to create a 120-dimension feature vector. Calibration images with known gaze coordinates are used to fit a linear regression with L2 regularization (ridge regression) that predicts the gaze location (x, y) from this feature vector. The gaze location for a new frame can then be predicted using the fit linear regression. We adopt the same basic framework, but instead of using raw pixel values as inputs to the regression model, we use learned feature embeddings from a neural network.

We used a hybrid CNN-transformer architecture to learn feature embeddings. Inputs to the embedding model are 144 × 36 px grayscale images. The convolutional part of the model is a residual network (He et al., 2016), using layer normalization in place of batch normalization. It consists of a 3 × 3 convolutional layer followed by three stages of two residual blocks each, with 64, 128, and 256 filters, for 13 convolutional layers in total. Max pooling after the first and second stages and again after the third reduces the image to an 18 × 4 grid of 256-dimensional features, which we treat as a sequence of 72 tokens. We added learned position embeddings to the tokens and then applied four layers of a standard transformer encoder (Vaswani et al., 2017) with 8 attention heads, a feed-forward width of 512, and dropout of 0.1. A single learned query then pooled the 72 tokens into one vector through attention (Lee et al., 2019), and a final dense layer with a tanh activation produced a 128-dimensional embedding for each image. The full model has 5.2 million parameters.

In addition to learning a mapping between pixels and features, we also learn a function that maps each image to a weight in the ridge regression. This allows the model to learn to deprioritize poor quality calibration images. To learn this mapping, we added a single layer with one unit on top of the output of the embedding model. This unit has a sigmoid activation function, to constrain weights to be in the range 0-1.

With image embeddings and weights computed, predictions are generated in two steps. First, we fit a weighted ridge regression to the calibration images. If 𝑋 is the matrix of calibration embeddings, 𝑌 the matrix of their known gaze coordinates, and 𝑊 a diagonal matrix of their predicted weights, the regression coefficients are 𝐴 = (𝑋 ⊤ 𝑊 𝑋 + 𝜆𝐼) -1 𝑋 ⊤ 𝑊 𝑌 . Second, we predict the gaze location of any new image by multiplying its embedding by 𝐴. The full model architecture is shown in Figure 3. The ridge regression is implemented as a Keras layer (Chollet & others, 2015), so gradients flow back through the regression into the embedding and weight layers, enabling us to train the model end-to-end. During training, 𝜆 = 0.1 and the regression has no intercept term.

Once the network is trained, the regression is the only part fit for each new participant, and it differs from the training version in two ways. First, gaze coordinates are measured from the center of the screen, and the center is added back to each prediction. This acts as an intercept fixed at the screen's center rather than estimated from the data, so a fit with little information, such as one from a few calibration points, falls back toward the middle of the screen rather than its top-left corner2. Second, the penalty is stronger, 𝜆 = 3; of the values from 0.1 to 30 we tried, this one gave the held-out participants (Section 4) the lowest median error averaged over calibrations of 3 to 144 points, though anything from 2 to 10 was within 0.1 percentage points of it. Each frame captured at a calibration point is its own row of 𝑋, and the weights in 𝑊 are rescaled to average 1.

Because we used the held-out participants to choose 𝜆 and to guide some later development of the model, we treat them as a development set rather than a test: the results in Section 4 may be somewhat optimistic. The validation study (Section 6) is an independent test, with new participants who played no part in developing the model.

3.1 Training

We trained the model using all participants with a complete set of 144 videos in the training data (N = 1,747; this includes one participant who later asked to be removed from the public dataset). In each epoch, we used one frame from each trial's video, drawn at random from up to seven frames after the participant's gaze had settled on the target (frame 3 through the fourth-to-last frame); trials with no frame in that window used the first frame with a detected face. We trained the model in batches of 5 participants (720 images per batch). For each participant in a batch, we randomly selected between 8-40 images to serve as calibration and the remaining images were used as prediction targets.

We applied image augmentation at the level of the participant and at the level of individual frames. For each participant in a batch, we applied the same random geometric transformation to all 144 images, preserving geometric consistency between the images while enabling augmentation beyond the training set. The geometric augmentations included a 50% chance of a horizontal flip, rotation up to ±9°, zoom 0.9-1.1x on each axis, translation up to ±10% on each axis, and a perspective warp moving each corner up to 10%. Photometric augmentations were applied independently to each individual image. We varied brightness by ±25 gray levels, contrast by 0.9-1.1x, gamma 0.9-1.1x, and, with probability 0.4, added Gaussian noise with an SD of 1-5 gray levels.

We used the Euclidean distance between the predicted and target locations as the loss, averaged over the target images and normalized by the length of the screen diagonal so that a loss of 0.2 means that the prediction is 20% of the screen diagonal away from the target. Because gaze locations are expressed as proportions of the screen's width and height, we scaled the horizontal dimension by 16/9 in the loss function to reflect the most common aspect ratio.

Training ran for 70 epochs, using the AdamW optimizer (Loshchilov & Hutter, 2019) with the Keras 3.13 defaults (weight decay 0.004, β₁ = 0.9, β₂ = 0.999, ε = 10⁻⁷) and JAX as the Keras backend (Bradbury et al., 2018; Chollet & others, 2015). We started with a run of 20 epochs from a random initialization, then did a warm restart (Loshchilov & Hutter, 2017) for another 50 epochs. In both runs, the learning rate rose linearly (Goyal et al., 2017) from 10⁻⁶ to a peak of 3 × 10⁻⁴ (over 2 epochs in the first run and 1 epoch in the second) and then followed a cosine decay to 3 × 10⁻⁶ (1% of the peak) by the end of the run. Total wallclock time for training on a TPU v5e was about two hours, including evaluations on held-out data every 10 epochs.

We used the held-out data from 257 participants to measure model performance during development; Section 6 tests the model on new participants. We began by assessing model accuracy using a typical calibration routine. We calibrated the model with 25 points, arranged in a 5 × 5 grid (Figure 4 B), from the first phase of the test data, and then measured prediction error on all 144 points from the second phase. 4.3 What features predict model accuracy?

We measured a variety of image and pose features to examine how they correlate with model accuracy. Some of these we measured at the participant level (Figure 6 A). For example, the standard deviation of the distance between the eyes over the course of the entire session correlates positively with model error (ρ = +0.42). Changes in interocular distance are caused by moving closer to and further from the camera, and the model's accuracy drops when participants move like this. Of the 18 participant-level predictors, 10 were significantly correlated with model error after Holm correction. The strongest predictor was the model's own estimate of calibration quality. Recall from Section 3 that the model outputs a weight from 0 to 1 that is used to weight calibration points. These weights can also be computed for every prediction, and the median of these values over a session is a good predictor of the model's accuracy (ρ = -0.53). We also asked participants whether they were wearing glasses, and participants without glasses had significantly lower error (median 4.73%, n = 192, against 8.74%, n = 29 with glasses; Wilcoxon rank-sum p < .001; Figure 6 B).

We also measured features at the individual image level. One class of these features are how different they are from calibration images. We found that changes in head pose and brightness after calibration were all positively correlated with model error (Figure 7; median ρ from 0.05 to 0.09). Another class of features is momentary changes in eye state. Blinks are, as expected, positively correlated with error (median ρ = +0.13). Eye aspect ratio, which measures how open the eye is, is also correlated with error; when the eyes are more open accuracy improves (median ρ = -0.16). Finally, the model's calibration weight for an individual image is correlated with accuracy on that image (median ρ = -0.16). This suggests that this model-derived metric can be used to identify moments during an experiment in which eye tracking quality changes.

5 Using the Model in a Browser

To facilitate use in the research community, we have developed a JavaScript library that can be used to deploy SaccadeJS on any webpage, including those generated by popular experiment building tools like PsychoPy/PsychoJS (Peirce et al., 2019), lab.js (Henninger et al., 2022), and jsPsych ( de Leeuw, 2015; de Leeuw et al., 2023). The library is published on npm as @saccadejs/core. Documentation is available at https://saccade.jspsych.org. We do not go into depth on the use of the library in the paper, as it is liable to be out of date as the project evolves. Please refer to the online documentation for tutorials, guides, and reference material.

Every step runs in the participant's browser, on each frame of the webcam's video. Webcam images are first processed by MediaPipe's Face Landmarker (Grishchenko et al., 2020; Kartynnik et al., 2019), which places 478 landmarks on the face. From these we crop the 144 × 36 pixel image of the eyes, with the same preprocessing we used to build the training data (Section 2.2).

The trained network is exported to ONNX (Open Neural Network Exchange), an open format for neural networks that lets a model trained in one framework run in another (Bai et al., 2019). In the browser, ONNX Runtime Web (ONNX Runtime developers, 2021) runs the model on the participant's graphics card through the WebGPU API (World Wide Web Consortium, 2026), or, where WebGPU is not available, on the CPU through WebAssembly. The model file is about 20 MB.

In training, the model processes a set of calibration images alongside each target image. In inference, each image needs to pass through the network only once. The ridge regression is fit once, from the embeddings of the calibration images. After that, each prediction costs one pass through the network to get the frame's embedding, plus applying the fitted regression to that embedding to get the gaze coordinates.

As we show in Section 6.4.5, not all machines are fast enough to run these predictions as fast as the camera samples new images. In our validation study, machines with Apple Silicon chips or NVIDIA graphics cards ran the model in real time, machines with integrated Intel or AMD graphics ran it somewhat slower than real time, and machines without WebGPU, which run the model on the CPU, took about a quarter of a second per frame. In cases where the machine cannot keep up with real-time processing, one option is to save the cropped eye images in memory and process them on one or more separate background threads while the main thread is running the experiment. Our library incorporates a deferred mode to enable this. In a worst case, cropped eye images could be saved as part of the experiment data and the model could be run offline instead of in the browser.

5.1 Timing Correction

One of the limitations of webcam eye tracking compared to laboratory equipment is temporal accuracy and sampling rate. The sampling rate of laboratory equipment is often 100-1,000 Hz, while webcams typically sample around 10-30 Hz. This is an unavoidable drawback of webcam-based eye tracking. Temporal accuracy is also usually worse with webcam systems. Browsers timestamp when a display change is drawn and when a camera frame is captured, on the same clock, but not the physical delays in between: the screen takes time to show a change, and the camera takes time to expose, process and stamp a frame. Their sum is unknown, not reported directly by the browser, and varies across machines.

To solve this problem, we developed a timing calibration routine that measures this delay for each participant. For 15 seconds, the display switches between black and white at random intervals of 500-1,000 ms, and the participant's face and room reflect the change. For each candidate delay from 0 to 600 ms, we check whether the frame-to-frame change in camera brightness just after each display change matches its direction, and it selects the delay at which all of them best line up. (Correlating brightness with the blackand-white sequence directly does not work, because webcam auto-exposure quickly compensates for changes in overall brightness.) The routine flags the estimate as unreliable when the brightness changes are faint, do not narrow the delay to less than one frame, or disagree between the two halves of the recording. The result is subtracted from each camera frame's timestamp.

To validate this approach, we built a measurement device using an RP2040 microcontroller, a phototransistor contacting the screen and an LED in view of the webcam. Each time the phototransistor detected a brightness change, the device lit the LED after a known delay between 100 and 140 ms, varied at random so the change in LED brightness could not be confused with the screen's change. This gave us a known delay between the screen's actual change in brightness and a moment in the video. If the browser's camera was perfectly synchronized to the display change, the delay would be 0. We tested two different laptops (a MacBook and a Lenovo ThinkPad), using Google Chrome in each, in bright and dim room light. Because the camera's frame rate affects the estimate's precision, we ran the test with both 15 and 30 frames per second as our requested sampling rate.

We made 25 one-minute recordings and scored each 15 s segment as the time synchronization plugin does, giving 100 estimates. Uncorrected, the delay in the LED change was 61-108 ms (Figure 8 A). When we applied the correction factor, the gap was within 31 ms of the true value (mean -6.5 ms, SD 8.4). This is within the limit set by two sources of uncertainty that the software cannot control. A camera frame records light over a span of time rather than at an instant, which limits precision to half a frame duration, and the browser cannot observe exactly when the display shows a change, which is up to one display refresh (typically 1/60 s). All corrected values fell within half a frame plus one display refresh (Figure 8 B). In Section 6.4.3, we report further evidence that this works by measuring the timing of saccades with human participants.

6 Validation Study

In this section we report the results of a validation study. We collected data from Prolific users with no demographic restrictions in order to provide a generalizable estimate of SaccadeJS's performance in the situations it is likely to be used by the research community. We included a direct comparison with WebGazer as part of the study. We chose to run the comparison with WebGazer because WebGazer is by far the most popular approach to webcam eye tracking that is found in the literature. Many existing studies have characterized its performance on the kinds of tasks that behavioral researchers employ (Bogdan et al., 2024; Hutt et al., 2024; James et al., 2025; Muñoz et al., 2025; Prystauka et al., 2024; Psarra et al., 2026; Saxena et al., 2024; Semmelmann & Weigelt, 2018; Slim et al., 2024; Slim & Hartsuiker, 2023; Steffan et al., 2024; Van der Cruyssen et al., 2024; Vos et al., 2022; Yang & Krajbich, 2021). We use this comparison to give researchers who are familiar with the performance characteristics of WebGazer a clearer sense of the degree of improvement that SaccadeJS offers.

6.1 Participants

203 people from Prolific completed the experiment. We sampled people who had completed at least 20 Prolific studies, had at least a 98% approval rate, and had indicated that they would be willing to use a webcam to record video during an experiment. We excluded any Prolific IDs that participated in any of the prior data collection for developing the model. The protocol was approved by the Vassar College Institutional Review Board. The 203 participants were 19 to 64 years old (M = 32.5, SD = 9.6). 134 (66%) were male and 69 (34%) were female. In Prolific's simplified ethnicity categories, 93 (46%) were White, 46 (23%) Asian, 28 (14%) Black, 22 (11%) mixed, and 11 (5%) another ethnicity; 2 preferred not to say and 1 profile no longer had the information. Participants lived in 31 countries; the top five were India (35), South Africa (24), the United Kingdom (20), Brazil (15), and Spain (15).

We excluded 3 participants (1.5%) who responded to fewer than 85% of the color changes during the main task, since they may not have been reliably looking at the targets. All analyses below use the remaining 200 participants.

6.2 Procedure

The experiment can be tried in a browser at https://jspsych.github.io/saccadejs-demos/, as participants ran it but without saving data.

The experiment began with a welcome screen that asked participants to find a comfortable position in order to minimize movement during the 10-minute experiment. This was followed by a screen that required participants to press the spacebar, as a means of identifying any participants without a physical keyboard. We then asked participants to identify whether they were using an internal or external webcam (with accompanying illustrations for each). The experiment then requested permission to access the camera.

Once camera permissions were granted, the experiment became fullscreen. We then used the SaccadeJS preview plugin to show participants their webcam image and the eye crop area that is used for tracking. This plugin also identifies whether a face is in the webcam image, and times out after 60 seconds if no face is found. Next, we ran the SaccadeJS performance plugin to record the live frame rate and model run time followed by the SaccadeJS time-sync plugin to estimate the temporal delay in the camera recording. Finally, we measured the time required to run the encoder model on the machine and used this to determine whether the model could run on the machine's GPU or needed to run on a pool of CPU workers. From the participant's perspective, these checks took about three seconds while we displayed a "getting ready" message.

With the checks complete, participants viewed the task instructions: "A target will appear on the screen. Look at its center and keep your eyes there. When it jumps to a new place, follow it with your eyes. Now and then, the small dot in the center will turn orange. When it does, press space. Please keep your head as still as you can, and move only your eyes. " This screen included examples of the target with and without the orange dot. Participants then completed five practice fixations, in which three of the targets required a response. If the participant missed any of the responses, the trials repeated after a reminder about the instructions. Participants were screened out if they failed three rounds of the practice.

Participants completed three blocks, each containing 43 fixation points. Of the 43, 13 were randomly selected as targets in each block, requiring participants to press the spacebar in response to the color change. The 43 points were selected by combining two grids and a small selection of random locations. 25 points came from a 5 × 5 grid, spaced at 5%, 27.5%, 50%, 72.5%, and 95% of the screen width and height, and provided calibration points (see analysis, below). The grid nests two smaller ones: a 9-point grid of its corners, edge midpoints and center (5%, 50%, and 95%), and a 13-point grid that adds the four points at 27.5% and 72.5%, SaccadeJS's default calibration. A 3 × 3 grid, spaced at 15%/50%/85% provided nine more. The remaining 9 points were randomly placed, with the constraints that one point must appear in each cell of a 3 × 3 division of the screen, no point could be within 5% of the width/height of the edge of the screen, and no point could be within 4% of the width/height of the screen of any other point. Each point appeared for at least 1,600 ms. For target points requiring a response, the color change occurred 900-1,300 ms after it appeared, and stayed visible for 1,000 ms after that point. Pressing the spacebar turned the outer part of the fixation target green. In between each block, participants were required to wait at least 10 seconds, and when ready could progress to the next block by pressing the spacebar.

After all three blocks were complete, the browser exited fullscreen mode and participants completed a short set of questions. These asked participants whether they wore glasses or contacts during the session, to describe any technical problems, and to describe anything that may have interrupted looking at the targets during the session. Finally, data were uploaded and the participant was redirected to Prolific.

6.3 Data Recording

Our goal with the study was to run the WebGazer and SaccadeJS algorithms on identical images, so we used a modified version of the SaccadeJS library to record the information needed. Both algorithms start with the same facial landmark identification. From there, WebGazer generates two 10 × 6 px cropped grayscale images of the eyes and SaccadeJS generates a 144 × 36 px cropped grayscale image spanning the eyes and bridge of the nose. For the WebGazer crops, we saved the pixel data directly. For SaccadeJS, we attempted to run the encoding model live on the participant's computer. For participants whose device supported the WebGPU framework and was fast enough to encode a frame in less than 85% of the duration of one camera frame, we ran the model in real time. For other devices, where either the GPU was too slow to keep up with the frame rate or where WebGPU was not available, we queued each image in a pool and processed them using up to three spare CPU threads. From pilot testing, we found that machines with 4GB of RAM or less couldn't handle more than one background CPU thread, so we limited the processing to one thread on these machines. Any images that were not processed by the pool of CPU workers by the end of the experiment were uploaded as raw image crops. We processed these after the fact and then removed the raw images from the dataset to protect privacy.

In addition to the image features needed for WebGazer and SaccadeJS, we also collected a variety of metrics to help us identify potential predictors of model performance. From the facial landmark model, we recorded the 3D coordinates of 9 locations (tip of the nose, midline of the upper forehead, lowest point on the chin, the widest points on the left and right side of the face, and the inner and outer corners of both eyes), head yaw, pitch, and roll, and the aspect ratio of the box surrounding the open part of the eye (used, in part, for blink detection). For each image, we also recorded sharpness, brightness, and sensor noise. Finally, we measured several features of the participant's machine. We recorded their web browser type and version number, operating system, whether the browser claims to be a mobile browser, the refresh rate of the display, the screen size in pixels, the WebGL version, CPU core count, device memory, whether WebGPU was available and if so what GPU adapter was used, camera resolution, and measured frame rate.

All data for this study are available on Zenodo at https://doi.org/10.5281/zenodo.23213276.

6.4 Results

Throughout the entire analysis, we measure spatial distances in percentage of the diagonal of the screen. For example, a distance of 50% would be equal to the distance from a corner of the screen to the middle. For remote studies, where controlling viewing distance is challenging at best, we think this gives readers a clear sense of the magnitude of the errors given typical viewing configurations for the population. As a rough guide, on a 14-inch laptop screen viewed from 60 cm, 1% of the diagonal is about 3.6 mm, or 0.34° of visual angle.

6.4.1 How spatially accurate and precise is SaccadeJS?

Our first aim was to characterize the spatial accuracy and precision of SaccadeJS. We calibrated each model using the first block's 25-point grid and then measured the model's predictions on all 43 points in the second and third blocks. For SaccadeJS, we used all recorded feature vectors at each calibration point, weighted by the model's quality score. For WebGazer, we used its standard click calibration: a click stores the features of the most recent camera frame, once, so we used one frame per calibration point, the one nearest the middle of the scored window, as at a click. WebGazer keeps only the 50 most recent clicks, and we used its default ridge penalty. Neither tracker's predictions were smoothed. WebGazer applies a Kalman filter to its predictions by default; we turned it off, since SaccadeJS's predictions are not filtered.

Smoothing could be applied to either tracker's output, and would improve the precision of both. We used measurements taken from 600-1,600 ms after the target appeared, leaving a wide window for the initial saccade to settle. As shown in panel A of Figure 9, SaccadeJS is more accurate than WebGazer for 195 of 200 participants (97.5%). We took the median error of each participant's predictions. With SaccadeJS, the median participant's error was 4.12% (IQR 3.01-6.20%); with WebGazer, it was 9.43% (IQR 7.01-11.88%). Within participants, WebGazer's error was a median of 2.2 times SaccadeJS's (IQR 1.8-2.6). The vast majority of predictions made by SaccadeJS (86%) were closer to the target than the median participant's error with WebGazer (panel B). To characterize the precision of both systems, we calculated the standard deviation of each participant's predictions around the mean prediction for each target, combining the horizontal and vertical directions, and pooled this across all targets (excluding targets with only 1 prediction). Because it is measured from the mean prediction rather than the target, this measure does not include accuracy.

SaccadeJS's precision was better for 200 of 200 participants (100.0%). With SaccadeJS, the median participant's SD was 4.04% (IQR 2.80-5.26%); with WebGazer, it was 6.89% (IQR 5.20-9.14%). Within participants, WebGazer's SD was a median of 1.8 times SaccadeJS's (IQR 1.5-2.1). The vast majority of predictions made by SaccadeJS (92%) were closer to their mean prediction than the median participant's SD with WebGazer (panel B of Figure 10).

To give a sense of the methodological impact of the improved accuracy and precision of SaccadeJS relative to WebGazer, we asked how many equal-sized square areas of interest could be used in an experiment such that 90% of the measured predictions fall inside the correct AOI if the participant is looking at the center of the AOI. We calculated this by finding the smallest square that held 90% of the samples around all the fixated targets in the experiment. We then determined the maximum number of rows and columns that could be used with this square size, assuming a 16:9 aspect ratio screen. This was the most common aspect ratio in our experiment (79% of participants' screens).

Figure 11 shows the computed layouts for participants at the 25th, 50th, and 75th percentile of error. SaccadeJS can support much smaller AOIs than WebGazer across the distribution of model performance. The WebGazer results are largely consistent with previous work characterizing WebGazer's performance as being sufficient for studies with screen halves or quadrants, but not smaller AOIs (James et al., 2025; Semmelmann & Weigelt, 2018; Slim & Hartsuiker, 2023; Yang & Krajbich, 2021).

We also looked at where on the screen errors are larger. We started by dividing each individual frame's error by the median error for that participant. We then grouped frames into a 5 × 5 grid, and took the median ratio for the participant in each cell. Finally, within each cell, we took the median across the 200 participants. For vertical error, we suspect this is because the eyelid tends to partially close when people look down, which reduces the visibility of the iris. But this does not explain the error at the sides.

6.4.2 How much calibration does a study need?

SaccadeJS and WebGazer can both be calibrated using an arbitrary set of calibration points. To provide researchers with guidance on how and when to calibrate, we measured the effect of different calibration protocols on accuracy. This was possible because we saved image features and embeddings instead of the normal usage of both systems where only gaze predictions would be saved after calibration. In each block of 43 points, the 25-point calibration grid also contained the 9-point and 13-point grids as nested subsets.

As shown in the left panel of Figure 13, the accuracy of predictions for SaccadeJS is relatively stable across the three calibration sets, but there is a reliable small gain in improvement with more calibration points. Going from 9 to 25 points lowered SaccadeJS's median error from 4.32% to 4.11%; within participants, the mean gain was 0.53 percentage points (95% CI 0.36 to 0.71); error was lower with 25 points for 152 of 198 participants. WebGazer shows a similar small but reliable improvement as the number of calibration points increases. Its median error fell from 10.12% to 9.42%, a mean gain of 0.69 percentage points (95% CI 0.49 to 0.88), and was lower with 25 points for 148 of 198 participants.

The middle panel of Figure 13 illustrates the effect of drift from calibration. Below, each value is the median of participants' median errors, with the interquartile range across participants. Focusing on the SaccadeJS results, accuracy is highest for points that are presented immediately after calibration, at 2.95% (IQR 2.14-4.30%), and then it degrades after only a few minutes. One block later, about 1.8 minutes after calibrating, error was 3.77% (IQR 2.59-5.36%), and two blocks later, about 3.3 minutes after, it was 4.60% (IQR 3.09-6.43%). The median rose by 56%, and error was higher two blocks later for 172 of 199 participants. WebGazer drifted as well, from 7.37% (IQR 6.03-9.25%) to 9.85% (IQR 7.35-12.69%), a 34% rise in the median.

Given the small gains in increasing the number of calibration points and the larger losses in accuracy with time since calibration, we tested a calibration scheme where participants calibrate on 9 points instead of 25, but recalibrate at each block. This was a substantive improvement over a single 25-point calibration at the start of the experiment. In the first block, where both calibrations were equally recent, the 25-point calibration was slightly more accurate for SaccadeJS: 2.95% (IQR 2.14-4.30%), against 3.35% (IQR 2.46-5.28%) with 9 points. In later blocks, recalibrating did better: 3.52% (IQR 2.44-4.93%) vs 3.77% (IQR 2.59-5.36%) in the second block, and 3.43% (IQR 2.43-5.01%) vs 4.60% (IQR 3.09-6.43%) in the third, where it was more accurate for 144 of 198 participants. WebGazer showed the same pattern: in the third block, 7.89% (IQR 6.62-9.65%) with recalibration, against 9.85% (IQR 7.35-12.69%) without. The 9-point calibration takes only about 15 seconds (nine targets at the task's median of 1.7 s per target, faster than the 1.9 s in Section 4.2, whose task waited for each detection response), so for maximum accuracy, we would recommend researchers do a small amount of calibration regularly throughout the experiment.

6.4.3 What is the temporal accuracy of SaccadeJS?

As described in Section 5.1, the temporal accuracy of webcam eye tracking has historically been poor due to unmeasured and unknown delays between the clock that controls the display and the clock that timestamps video frames. We developed a procedure that measures this delay and corrects for it. In this Prolific experiment, we do not have ground-truth timing measurements; however, saccades to a target that steps to a new position typically begin about 200 ms after the step (Carpenter, 1988; Saslow, 1967). As a laboratory reference, we used the random-saccade task of GazeBase (Griffith et al., 2021), an open dataset in which 322 young adults followed a target that jumped to a new position within ±15° horizontally and ±9° vertically once a second, recorded at 1,000 Hz with an EyeLink 1000. In this analysis, we check whether the correction algorithm produces estimates of saccade latency that are in line with these data.

We measured camera delay using the time sync plugin at the start of the experiment. As shown in Figure 14 A, the estimated delays had a median of 84 ms (range 20-275 ms) among the 162 participants whose measurement the plugin judged reliable. To measure saccade timing with the variable and low sampling rates of the webcams, we estimated when the gaze crossed the midpoint of a line between the old and new targets. We applied a linear interpolation of gaze so that the sampling rate of the camera did not bias the measurement. Without it, the crossing would be placed at the first frame past the midpoint, which comes later on average the fewer frames a camera records, so slower cameras would produce slower saccades. We used the repeating calibration strategy described in Section 6.4.2 to improve accuracy of the estimates.

As shown in Figure 14 B, without correction there is a positive relationship between the measured camera delay and the saccade latency (r = 0.48, slope 0.76 ms per ms). This is as expected for uncorrected measurements. After subtracting out the camera delay for each participant, the estimate of saccade timing drops from 297 ms (IQR 276-322 ms) to 206 ms (IQR 189-236 ms) for SaccadeJS, and from 294 ms (IQR 271-325 ms) to 204 ms (IQR 184-233 ms) for WebGazer (Figure 14 C). We timed GazeBase's saccades the same way as ours, when gaze crossed halfway to the new target; their participants' median latencies were 224 ms (IQR 215-235 ms). The midpoint comes about half a saccade's duration after the saccade's onset (Carpenter, 1988), the time most studies report; in GazeBase, a median of 23 ms after. When we compare our estimates to GazeBase's, we see that the corrected estimates of saccade timing are in line with the laboratory distribution. 6.4.4 What features predict eye tracking accuracy?

As described in Section 6.3, we measured several different features of sessions (participant level variation) and individual frames (single prediction level variation). Each measure is defined, with the code that computes it, in R/measures.R in the paper's repository (https://github.com/jspsych/saccadejs-paper). Here we focus on what measurable aspects of the participant and individual video frames predict gaze accuracy. We report Spearman rank correlations because of the strong skew of the error distribution.

Figure 15 shows the correlations of participant-level features. Besides the model's quality weight, which we return to below, we measured 12 characteristics of each recording. After Holm correction, 4 were statistically significant predictors of SaccadeJS's accuracy (2 for WebGazer: the first two below). Participants with (1) more variance in their head roll over the course of the session (ρ = +0.34), (2) lower contrast in the eye images (ρ = -0.33), (3) smaller interocular distance -which likely reflects sitting further away from the camera (ρ = -0.26), and (4) blurrier images (ρ = -0.25) had more error in the gaze predictions.

At the level of individual images, measuring correlations within a participant (Figure 16), we checked two kinds of image properties. One was to measure change since calibration. Here, everything we measured had a small but statistically significant correlation with accuracy for both trackers (SaccadeJS median ρ from 0.05 to 0.10). Time since calibration, changes in head pitch, roll, and yaw, changes in interocular distance, shifts in head position, and changes in eye brightness were all correlated with increased error. We also measured some features of the eye images that changed moment to moment. Eyes that are more open correlate with lower error, blinks correlate with higher error, and increased blur of the image correlates with higher error.

The SaccadeJS model outputs a quality weight for each image. This model-derived measure was among the strongest predictors of error (median ρ = -0.14), on par with eye openness (median ρ = -0.15) and blinks (median ρ = +0.14). This measure is computed in real time, and could be used by researchers to estimate when prediction quality is poor. It also predicted which participants would be tracked well. Each participant's median weight was the strongest correlate of their median error (Figure 15; ρ = -0.62), and it predicted WebGazer's error too (ρ = -0.48), even though WebGazer does not use it. So the weight reflects the quality of the recording, not only SaccadeJS's confidence in its own predictions. No demographic features (age, ethnicity, sex) were statistically significant predictors of error. Participants who wore glasses (n = 39) had higher error (median 5.58% vs 3.82% for SaccadeJS; 11.16% vs 8.85% for WebGazer), and participants who used a separate rather than built-in camera (n = 28) had less error (2.86% vs 4.28% for SaccadeJS; 6.86% vs 9.73% for WebGazer; Figure 17). The camera result surprised us, as we expected the consistent placement of built-in webcams to be beneficial. Our working hypothesis is that separate cameras tend to be higher quality. Their images of the eyes had 42% more contrast and 30% less sensor noise than built-in cameras. Contrast was one of the strongest participant-level predictors of error (Figure 15).

6.4.5 What hardware does SaccadeJS need?

The major tradeoff of SaccadeJS relative to WebGazer is that it is a more computationally expensive algorithm to run. In our sample, we found that most of the devices used by participants were unable to deliver gaze predictions at the sampling rate of the webcam. As shown in Figure 18 A, only 35% of machines kept up with their camera (delivering at least 90% of its frame rate); the median participant received 10 gaze samples per second from a camera running at 23 frames per second.

The SaccadeJS model is optimized to run on a GPU, which, when available, is accessed through the browser's WebGPU interface. In our sample, machines with Apple Silicon chips or an NVIDIA GPU took about 10-12 ms to encode one frame (medians), while encoding on the CPU took 375 ms per frame (Figure 18 B). Most machines with WebGPU capability were unable to keep up with the camera frame rate. These were generally chips with integrated graphics units from Intel and AMD. Encoding on these chips took a median of 54-69 ms, which is just on the edge of being able to encode in real time with a 15 fps camera.

There are two reasons that we are optimistic that real-time performance will be possible on many more machines soon. First, we have explored quantized versions of the model that take up ~25% of the memory that the floating point version requires. These deliver nearly identical prediction quality, but we haven't collected data with them on a wide variety of machines. Second, the availability of dedicated GPU hardware is becoming much more common in entry-level laptops, so we expect these estimates to become obsolete quickly as more participants get access to the kinds of devices that supported real-time tracking.

7 Conclusion

SaccadeJS offers substantial improvement in the accuracy and precision of real-time eye tracking for browser-based experiments. Researchers can use SaccadeJS to reliably distinguish between much smaller AOIs than WebGazer, enabling online eye tracking research to move beyond designs with halves and quadrants. Furthermore, with a brief temporal calibration, the accuracy of webcam timestamps can be improved to the point where the major limiting temporal factor is the sampling rate of the webcam instead of synchronization.

Performance of SaccadeJS depends on the participant's environment and device. We recommend that researchers include instructions that encourage a well-lit face (enhancing contrast around the eyes), minimizing head movement during the task, and sitting closer to the screen. Based on the results of our validation study, we modified our initial implementation of the @saccadejs/plugin-preview plugin to provide feedback to participants on their environment. The plugin measures interocular distance and contrast in the eye region, and advises participants if they need to move closer/further or improve lighting conditions. How researchers choose to calibrate the system also matters. Researchers can also improve accuracy through periodic short recalibrations instead of using longer one-off calibrations at the start of the task.

We do not expect that the particular gaze prediction model we developed is an optimal one and we encourage the use of our dataset to discover improvements. The SaccadeJS dataset is the largest of its kind, and the first that is specifically targeted at the kinds of eye movements that participants make when using a laptop or desktop screen in an uncontrolled environment. We hope that its availability allows gaze models for online research to be compared on common data. SaccadeJS's own scores on the held-out participants are development-set scores, since we used them while developing the model.

One significant limitation of the current model is that it was able to keep up with the camera in real time on only 35% of the machines in our validation study sample. As a result, we have built a deferred mode into the SaccadeJS library. This mode operates like the version we built for the validation study: image crops are taken in real time and saved in a memory queue. One or more CPU threads then processes these in the background, staying off the thread used to run the experiment. The downsides of deferred mode are that it cannot be used for any study that relies on real-time gaze predictions and, at some point during the study, the eye tracking needs to be off while the queue catches up. This can be done during brief breaks between trials or at the end of the experiment. Optimistically, we expect consumer laptop hardware to continue to improve in ways that are specifically targeting GPU and GPU-like computation with the increasing adoption of neural networks for language and image processing on these devices. For example, Intel and AMD have both started producing integrated chips with Neural Processing Units (NPU) that are designed to support neural network operations. A WebNN API is currently partially supported by some browsers, with widespread adoption likely in the next few years. This should further improve the ability of browsers to run models like SaccadeJS.

Finally, SaccadeJS is an open-source project and we welcome contributions from the research community. Contributions could include new gaze prediction models, jsPsych plugins to support different kinds of eye tracking methods, tutorials, and bug fixes. We invite potential contributors to read our contribution guide on our GitHub repository, https://github.com/jspsych/saccadejs/.
