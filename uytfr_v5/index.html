How Ethics Approval Check works

This module searches for statements of ethics approval, IRB approval, institutional review board approval, and related terms.

Patterns are designed to capture:

Human research committee names - Institutional Review Board / IRB (US standard) - Independent Ethics Committee / IEC (ICH-GCP international clinical trial term) - Ethical/Ethics Review Board (generic) - Ethics (Advisory/Review) Committee/Board/Panel/Sub-committee - Research Ethics Committee/Board/Panel (UK/Canada/Australia) - Medical Ethics Committee - Human Subjects/Research Committee / Human Research Ethics (Advisory) Panel - Committee for/on the Protection of Human Subjects - Committee on (Health) Research Ethics - Office of Research Ethics - Abbreviations: IEC, REC, REB, ERB, METC, DEC. IRB and IEC are kept unconstrained as they are not observed to collide in practice. - Dutch: Medisch-ethische toetsingscommissie (METC) - French: Comité d'éthique / Comité d'Ethique

Animal research committee names - Institutional Animal Care and Use Committee / IACUC (US standard) - Any sentence containing animal(s) and committee (or board/panel) within ~5 words of each other — catches Experimental Animal Care and Use Committee, Animal Ethics Committee, Animal Welfare Board, Animal Welfare Ethical Review Body, etc. - UK: Animal Welfare Ethical Review Body / AWERB - Dutch: Dierexperimentencommissie / DEC (see DEC constraint above); Instantie voor Dierenwelzijn / IvD - German: Tierversuchskommission / TvK (advisory committee under §15 Tierschutzgesetz) - French: Comité d'éthique en expérimentation animale / CEEA; Comité d'éthique animale - Spanish: Comité de ética en experimentación animal / CEEA

Approval phrasing - Ethics/Ethical (approval|clearance) [was] (granted|obtained|received|given|secured) - Ethically approved - Approved by the (ethics|irb|institutional|independent|local|review|research) ... - This/The study/protocol/experiment/procedures/methods/research [was] (approved|reviewed) by - Study was ethically approved - (Followed|met|follow) the ethical (guidelines|standards|requirements) - In accordance with ... ethical (guidelines|standards) - Ethics protocol - Approved under (protocol|reference|number)

Waiver / exemption - Ethics/Ethical (waiver|exemption) - IRB (waiver|exemption|exempt) - Exempted from (ethics|irb|institutional review) - Waived by the (ethics|irb|institutional|review) (committee|board) - Deemed exempt

Declaration of Helsinki - Declaration of Helsinki / Helsinki Declaration

This module uses regular expressions to identify sentences that contain a statistical power analysis. The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold” or “legend”). Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). When none of these is found, the report flags it as a reproducibility gap: package versions may drift between when the analysis was run and any later reproduction attempt.

If you want to extend the package to perform additional checks on code files, or make the checks work on other types of code files, reach out to the Metacheck development team.

Checking code requires downloading its file contents. For a paper whose repository is on Dryad, this never succeeds unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (listing the repository’s files does not need one). Without a key, every Dryad-hosted code file is listed but unchecked, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures recorded in the manifest.

How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Despite substantial concern about how technology use relates to mental health, research attempting to identify beneficial or harmful smartphone activities has yielded mixed results.

Here, we show that abstracting away from specific activities, their transition patterns across time relate robustly to user mental health. To quantify this transition structure, we develop a novel network analysis method to capture how each phone user journeys across Apps within a smartphone session. Across two independent datasets, including an exploratory UK sample aged 18-22 (n = 82), and a preregistered replication in the USA aged 15-18 (n = 565, ABCD cohort), we show that 'App-journey' networks relate consistently to user mental health. For example, users with higher anxiety symptoms transition to a wider variety of Apps within each phone session (higher network density) and are less likely to confine each session to repeated groups of Apps (lower network modularity). In contrast, we find no relationship between ADHD and network modularity or density, suggesting that App-journey networks may distinguish among different mental health profiles. Additionally, in the exploratory dataset, Apps which users describe as more 'automatic' are more central in App-journey networks. In summary, we uncover a relationship between the temporal structure of digital activity and specific mental health symptom categories, which generalizes across samples and age groups. The temporal structure of digital activity may thus represent a hitherto neglected, potentially clinically-relevant dimension of digital behaviour for future research and interventions.

Main Text Introduction

There is considerable concern about the impact of excessive smartphone use on young people's mental health (1) (2) (3)). Yet research relating mental health to time spent on one's phone, and even to specific phone activities, has uncovered inconsistent associations, ranging from positive, to negative or no relationship (4-7).

One possibility is that smartphone activities which may not be individually problematic could become harmful in the context of phone use because of the way that users transition between these activities. While phones offer new opportunities to communicate with friends, learn information and more, they also intermix these activities in the same device and format in unique ways. As such, the structure of how digital activities interact may itself generate benefits and harms that cannot be inferred from studying single activities in isolation.

The patterns of inter-relationship between different phone activities within a session could plausibly be both a consequence and a cause of poor mental health. When phone sessions deviate from original intentions, or begin with no specific goal, they are more likely to lead to regret (8, 9). For example, spending time messaging a friend can cause subsequent regret if one had originally opened the phone just to use the calculator, but might not cause regret if one had opened the phone with the purpose to communicate (10). Given that regret is associated with negative mood (11), smartphone use featuring higher interference between different activities could lead to poorer mental health, marked by cycles of negative mood or depressive symptoms (9). Conversely, depression and anxiety are often comorbid with reduced concentration and attentional control, which could increase the risk of distraction during phone use, causing greater interference between different phone activities (12) (13) (14). In this way, the structure of different phone activities across time might relate to mental health via bi-directional causal pathways. Therefore, this structure could be an informative dimension when understanding the link between smartphone use and mental health.

To our knowledge, most previous studies measuring transitions between smartphone activities have relied on participant self-reports (8, 9, 15). However, self-report involves high participant burden, introduces potential demand characteristics and also requires sufficient self-awareness for accurate reporting (16, 17). Alternatively, approaches using objective data often enumerate App transitions without situating them within the wider context of holistic activity journeys, which may carry additional information (18). In contrast, inferring characteristics of smartphone activity journeys directly from objective data could be uniquely informative, as well as representing a scalable, generalizable and privacy-preserving method of quantifying a dimension of technology use which may be mechanistically related to mental health.

The present research

In this study, we develop a novel approach to quantify holistic transition patterns among different digital activities, and apply this to exploring the journeys between different Apps within a phone session. Using objective phone data, we construct networks representing the journeys each phone user takes across different Apps within a phone session, which we term 'App-journey' networks. As shown in Figure 1, in an 'App-journey' network, all Apps used by that phone user are network nodes, and the connection from one App to another represents the probability that if the phone user uses the former App in a session, they will subsequently use the latter App before ending their session (i.e., locking their phone) (Figure 1).

We constructed App-journey networks in two separate datasets, including an exploratory dataset (n = 82, UK-based, aged 18-22, collected by our research team), and a preregistered confirmatory dataset (n = 565, USA-based, aged 15-18, part of the Adolescent Brain Cognitive Development (ABCD) cohort study). The exploratory dataset was collected for this study, while the confirmatory dataset is a secondary data analysis.

In both datasets, phone data was passively recorded for approximately one week, including which Apps users had in the foreground at any time. Participants additionally completed a battery of mental health and other questionnaires. The combination of these different datasets allowed us to investigate whether any associations between App-journey network features and mental health generalized across samples varying in country, age and data collection context.

Hypotheses

We hypothesized that App-journeys would relate to a phone user's mental health. For example, the modularity of an App-journey network indexes the extent to which the user's Apps are organised into discrete 'modules', with each phone session predominantly employing a single module rather than journeying across unrelated modules. This might represent the extent to which someone uses each phone session for an intended activity (for social, work-related, information-gathering, or entertainment) rather than becoming distracted and journeying to other unrelated phone Apps once entering the phone. To investigate the relationship between App-journeys and mental health, we correlated features of App-journey networks with scores on mental health questionnaires, measuring selfreported levels of anxiety and depression (both datasets), OCD (exploratory dataset) and ADHD (confirmatory dataset).

We set out to answer three research questions, the first and third of which were preregistered in the confirmatory dataset (while the second was only analysed in the exploratory dataset due to data availability). First, do the global network properties of App-journeys relate to different mental health categories? Secondly, do the local network properties of specific Apps in these App-journey networks relate to the extent to which these Apps are subjectively experienced as 'automatic'? Finally, to contextualise our novel method with more traditional methods used to relate phone use to mental health in media effects research (6), we investigated whether time spent on one's phone related to mental health in our samples. Network modularity represents the extent to which the network is organized into distinct node 'communities', with higher modularity signifying many or stronger connections within each community and fewer or weaker connections between communities (Figure 1b). In the context of App-journey networks, higher modularity suggests that these communities stay relatively stable across sessions; in other words, the same Apps typically occur together in the same session rather than occurring with different Apps each session.

We found that in the exploratory dataset, network modularity negatively predicted mental health for all three questionnaires; depression (PHQ-8), anxiety (GAD-7) and OCD (OCI-R) (PHQ-8: β = -0.265 [SE = 0.108], p = 0.016, BF10 = 3.015; GAD-7: β = -0.254 [SE = 0.112], p = 0.021, BF10 = 2.428; OCI-R: β = -0.368 [SE = 0.104], p < 0.001, BF10 = 42.060) (Figure 2a, Table 1). In the confirmatory dataset, results relating depression and anxiety to modularity replicated in direction from the exploratory dataset (YSR DSM depression: β = -0.118 [SE = 0.042], p = 0.005, BF10 = 4.348; YSR DSM anxiety: β = -0.121 [SE = 0.042], p = 0.004, BF10 = 5.506).

However, in contrast to depression and anxiety, there was no significant relationship between modularity and ADHD, with substantial evidence for the null hypothesis of no relationship (YSR DSM ADHD: β = -0.035 [SE = 0.042], p = 0.410, BF10 = 0.131).

Overall, relating App-journey network modularity to mental health reveals that young people with lower levels of depression and anxiety symptoms exhibit more modular App-journeys.

Modularity also related to OCD symptoms in the exploratory dataset (we did not test OCD in the confirmatory dataset), but in the confirmatory dataset we found evidence against a relationship between modularity and ADHD symptoms. In other words, adolescents with lower levels of depression and anxiety typically use their smartphone Apps in more distinct communities, wherein community membership is consistent across phone sessions, and are also less likely to transition from one group of Apps to another group within a given phone session. We next related App-journey network density to questionnaire scores (Figure 2b). Network density is the proportion of actual edges in a network relative to the number of possible edges (Figure 1c). This can be understood as the extent to which phone users journey randomly across many Apps in each phone session, rather than taking the same journey across fewer Apps each time.

In the exploratory dataset, App-journey network density was significantly positively related to mental health symptoms, with denser App-journey networks predicting higher symptoms of depression, anxiety and OCD (PHQ-8: β = 0.

321 [SE = 0.106], p = 0.003, BF10 = 11.207, GAD-7: β = 0.310 [SE = 0.106], p = 0.005, BF10 = 8.508, OCI-R: β = 0.352 [SE = 0.105], p = 0.001, BF10 = 26.126). In contrast, in the confirmatory dataset, of the analysed mental health questionnaires, only anxiety showed a significant positive relationship with App-journey network density (replicating the direction in the exploratory dataset) (YSR DSM Anxiety: β = 0.088 [SE = 0.042], p = 0.037, BF10 = 0.792). In contrast, Bayes Factors showed there was substantial evidence for the null hypothesis of no relationship with depression (YSR DSM Depression: β = 0.061 [SE = 0.042], p = 0.004, BF10 = 0.260), and ADHD (YSR DSM ADHD: β = -0.036 [SE = 0.042], p = 0.392, BF10 = 0.134).

Overall, relating App-journey network density to mental health reveals that young people with higher anxiety symptoms exhibit denser App-journeys, but not those with higher depression or ADHD symptoms. Density also related to OCD symptoms in the exploratory dataset (we did not test OCD in the confirmatory dataset). This suggests that those with higher levels of anxiety journey to a wider variety of Apps within a session, with App connections less consistent across sessions.

Global network features summary

In summary, we investigated how the global App-journey network features modularity and density predicted mental health symptoms, and found similar relationships across both datasets among internalizing mental health categories, although a different relationship for externalizing ADHD. Increased anxiety symptoms were associated with lower App-journey network modularity and higher App-journey network density, while increased depressive symptoms were associated with higher network modularity in both datasets. In the exploratory dataset, OCD followed the same associations as anxiety and depression, being negatively associated with modularity and positively associated with density; this data was not collected in the confirmatory dataset. In the confirmatory dataset, ADHD symptoms showed no relationship with either App-journey network feature. This suggests that the transition patterns across different phone Apps relate to mental health, robustly across samples varying in country and age.

We next wanted to understand whether the location or role of specific Apps within Appjourney networks related to the likelihood that that App was subjectively experienced as 'automatic'. To this end, we compared local (node-level) network properties between the Most Automatic and Least Automatic Apps. In all, we compared node in-strength and out-strength, in-diversity and out-diversity, centrality, local clustering and betweenness, to gain a comprehensive understanding of node positions.

We first compared node strength, which is the sum of weights of all edges connected to a node (Figure 5a). This can be separated into 'in-strength' and 'out-strength', which are the sum of all in-weights and out-weights, respectively. Given that 'in-strength' represents the sum of the conditional probabilities that the App in question would be visited after any other App, a higher in-strength captures the intuition that there is a high probability of ending up on the App in question after visiting other Apps. In contrast, 'out-strength' represents the probability of transitioning to any other App after using the App in question (at any point in the same session), as opposed to simply ending the session. A higher 'out-strength' suggests that a phone user typically continues to more Apps after using the App in question (rather than just locking the phone immediately).

We then compared node centrality between Most Automatic and Least Automatic apps (Figure 5c). Centrality conceptually indexes the importance or influence of a node in the network. This concept builds on node-level properties like strength and diversity by considering also the node-level properties of other nodes in the network. Alternative measures of centrality can be distinguished by the different ways in which they weight constituent features. For example, 'eigenvector centrality' assigns relative scores to all nodes, with connections to other high-scoring nodes increasing each node's score. In contrast, 'coreness' is a measure of how centrally-embedded a node is within the network, such that nodes with high coreness are deeply embedded within the network's structure, by being connected to a higher number of subgroups.

We compared both eigenvector centrality and coreness between Most Automatic and Least Automatic Apps. Across participants, the Most Automatic App had both a higher eigenvector centrality (paired t-test: t(60) = 5.375, p < 0.001, BF10 = 12,091.24) and higher coreness (t(60) = 4.365, p < 0.001, BF10 = 402.814). In summary, across two measures of centrality, the Most Automatic App was more central in App-journey networks than the Least Automatic App. This is consistent with the interpretation that regardless of a user's original purpose for opening their phone, they will still more typically end up using the Most Automatic App.

Finally, we compared the local clustering coefficient and betweenness between the Most Automatic and Least Automatic Apps (Figure 5d). The local clustering coefficient quantifies the extent to which a node's neighbours are also interconnected with one another. We computed this using a weighted generalisation of the clustering coefficient, applied to the undirected version of the network, where edge weights reflected connection strength (i.e., stronger connections corresponded to higher weights). This measure therefore captures the degree of local "triadic closure" around each node, taking into account both the presence and strength of connections between neighbouring nodes.

In contrast, betweenness quantifies the extent to which a node lies on the shortest paths between all other pairs of nodes in the network and can therefore be interpreted as an index of how frequently a node acts as a bridge between distinct node communities. We computed betweenness centrality on the directed weighted network, using edge weights reflecting connection strength, such that stronger connections contributed to shorter path lengths.

Local clustering coefficient and betweenness centrality capture complementary aspects of network organisation. The local clustering coefficient indexes the tendency for a node's immediate neighbours to be densely interconnected, reflecting locally cohesive or "clustered" neighbourhood structure. In contrast, betweenness centrality captures the extent to which a node connects different parts of the network, reflecting a more global bridging or brokerage role. Accordingly, nodes with high clustering tend to be embedded within tightly interconnected local neighbourhoods, whereas nodes with high betweenness tend to link otherwise separate regions of the network.

Mean time spent on one's phone per day did not significantly predict scores on any mental health questionnaires in the exploratory dataset. Discussion

In this study, we ask whether the relationship between digital behaviour and mental health depends not just on specific harmful or beneficial activities, but also on how users transition between activities. We developed a network analysis method to extract properties of each participant's activity journey within a phone session, and related these to mental health across two independent datasets: an exploratory UK sample (n = 82), and a preregistered USA replication (n = 565). Using this novel approach, we found that the modularity and density of App-journey networks was related to symptoms of anxiety and depression (both datasets), as well as OCD (exploratory only), but not to symptoms of ADHD (confirmatory only). Furthermore, App-specific analyses in the exploratory dataset revealed that Apps which participants reported using most automatically were more central in App-journey networks than Apps participants reported using least automatically.

Together, these findings suggest that the transition journeys across smartphone activities may have relevance for mental health and experiences of automatic phone use. This new dimension of smartphone use may prove a fruitful target for future mental health research and digital wellbeing interventions, helping to move media effects research beyond focusing on time spent or specific activities in isolation.

Relating global App-journey network structure to mental health

We constructed 'App-journey' networks to quantify how users journey across different smartphone activities (operationalized as Apps) in a phone session. This approach abstracts from the specific activities engaged with on a phone, and instead focuses on how a user journeys across different activities over time. This allows us to extract signatures of phone behaviours predictive of mental health and attentional control, which can generalize across samples, as well as potentially be more robust to the constantly changing contents of specific phone activities (26, 27).

We first found that global features of App-journey networks, modularity and density, predicted mental health symptoms. In the context of App-journey networks, modularity can be interpreted as the extent to which Apps are typically used together in subgroups during a given phone session, as opposed to the user journeying from one subgroup to another within each session. On the other hand, density describes how many pairs of Apps were used in the same session at least once, as a proportion of possible pairs of Apps that could have been used together. We found that anxiety related to both modularity and density, while depression related only to modularity. We additionally examined only OCD in the exploratory dataset, and found that both OCD symptoms were predicted by lower modularity and higher density, following the same pattern as anxiety and depression. However, preregistered analyses in the confirmatory dataset found no relationship between ADHD symptoms and App-journey network features considered, despite their relationship to objective time spent on one's phone. We note that this preregistered analysis of ADHD data was not tested in the exploratory dataset.

This dissociation of results between symptoms of internalizing disorders anxiety, depression and OCD, compared with externalizing ADHD, suggests that different mental health profiles may have distinct App-journey networks. Specifically, phone users with more modular, less dense App-journey networks have lower symptoms of anxiety but there is no evidence for a relationship with ADHD. Our study was cross-sectional, and therefore there may be several, non-mutually exclusive mechanisms underlying the observed associations between Appjourneys and mental health. One possibility is that more 'modular' networks represent the extent to which Apps are organized into different 'modules', each representing a different typical phone need -for example, social connection, learning information, work-related activities, and games. In this context, a more modular and less dense App-journey network might index the extent to which a given user typically uses their phone for a single activitytype per session, rather than deviating from their original intended activity once opening the phone, or having no particular intended activity.

Greater modularity might suggest that an App-journey was more intentional or purposeful.

The psychological literature refers to purpose-oriented behaviour as 'goal-directed' behaviour (28). It might be that smartphone environments, by grouping attractive activities within the same tool, pose a novel challenge for goal commitment when fulfilling these goaldirected uses. Conversely, and mutually compatibly, less goal-directed phone use could increase regret (8), and inability to stay on task may lower mood with adverse mental health outcomes. Finally, it is possible that there is no causal relationship between mental health and phone use, and instead that a third factor, such as daily activities, influences them both.

Self-reported 'automatic' Apps as network attractors

Along with comparing global network features across participants, in the exploratory dataset we additionally analyzed local features of specific nodes (Apps) within these networks which participants reported as using either more or less automatically, within participants.

Participants reported social media as the most popular category for 'Most Automatic' Apps, with the Instagram as the most commonly reported (38 out of 80 responses). Compared with the 'Least Automatic App', the 'Most Automatic App' had a higher node 'in-strength'. This suggests that within a phone session, the user is more likely to transition from other Apps to the Most Automatic App than the Least Automatic App. We also found that the Most Automatic App had a higher in-diversity and lower out-diversity, suggesting that a greater range of Apps transition to it, but that there is a lower range of Apps that it transitions to.

Furthermore, across two measures of centrality, eigenvector centrality and coreness, the Most Automatic App was more central in App-journey networks than the Least Automatic App. Additionally, the Most Automatic App had lower local clustering and higher betweenness, suggesting it is more likely to connect distinct App communities than the Least Automatic App, which is more likely to be confined within a specific community. This is consistent with an 'attractive' function wherein phone use with any array of intentions converges more often to using the Most Automatic App.

This pattern likely reflects habitual or more automatic opening of the Most Automatic App (29). While behaviors are mostly initiated for the first time by motivational factors like goals or intentions, frequently repeated behaviors can become habitual or automatic (30). This means they are performed with less regard for these more conscious motivations and are instead activated upon perception of the context in which they were performed in the past.

In the case of Apps, context cues to habit performance might include notifications, the sight of the App icon on the smartphone screen, or other environmental features and even emotional states or feelings like boredom (24, 31).

Given that Most and Least Automatic Apps were identified through self-report, we do not necessarily use these comparisons to index the Most and Least Automatic Apps objectively, but rather to compare automaticity as subjectively experienced by the user. Sanity checks did ascertain that these self-reports corresponded to objective differences in the relative way in which the two Apps were used, with the Most Automatic App appearing at least once in a higher proportion of sessions and having a typically longer App-session duration. These findings therefore suggest that the role of an App in an App-journey network is related to the extent to which it is experienced as being used automatically.

Time spent

In our final preregistered analysis, we attempted to replicate previous literature which has focused on relating mental health to time spent on digital media (6, 32). We found no evidence for an association between objective time spent on the smartphone and mental health in the exploratory dataset, with Bayes Factors suggesting support for the null hypothesis of no relationship. In contrast, we found a postive relationship between all three mental health questionnaires -anxiety, depression and ADHD -and time spent, in the preregistered confirmatory dataset.

Limitations and future directions

Overall, in this study we have demonstrated that the temporal relationships between different digital activities relates robustly to specific mental health profiles. Importantly, our study was cross-sectional, meaning that any causal interpretation of relationship between this behaviour and mental health is not yet warranted.

However, this new method of measuring smartphone behaviour paves the way for investigation of causes and effects of different digital journey types, as well as potentially, if a causal relationship is found, informing smartphone interventions. For example, longitudinal research in future could establish whether increased modularity predicts worsened mental health, or vice versa. Further, intervention studies could alter mental health states or phone use modularity and examine the effects of this on smartphone behaviour or examine the effects of feedback about smartphone modularity on mental health or behaviour. If a relationship between App automaticity and network centrality is established, this could also be used to deliver interventions at the App-level which help identify which Apps are most problematic for a given user (33).

Conclusion

Properties of App-journey networks are linked to mental health across two independent datasets, including a preregistered replication. In particular, young people with higher anxiety symptoms exhibit less modular 'App-journey' networks, suggesting lower behavioural organisation across digital activities, although this relationship does not extend to all mental health profiles, with no relationships found between App-journey networks and ADHD. This novel method of quantitatively characterizing phone behaviour from objective data opens new avenues to identify problematic phone use which go beyond time spent. In this way, we hope this approach will help to facilitate better understanding of the causal pathways and intervention targets for healthier smartphone use.

Exploratory dataset

Participants

Data Collection App

Our research team developed a novel Data Collection App in order to collect data for this study. The Data Collection App is downloaded onto a participant's mobile phone, and while downloaded records the following data between when the phone is unlocked and unlocked: the timestamps for when touches (i.e., taps and swipes) occur on the touchscreen, timestamps of unlocking and locking the phone, and the timestamps and names of Apps running in the foreground of the phone.

For ethical reasons to protect participant privacy, the App also included a 'pause' button which, when pressed, would halt all data collection.

Data collection would resume automatically if the pause button was pressed again, or if 60 minutes had passed.

Data collection protocol

All participants began with an introductory video-call with a member of the research team, where they were introduced to the study and downloaded the App onto their phones. They were instructed to move the App widget off the immediate homescreen to minimize interference with their normal phone experience routine. Participants then kept the App recording their data for approximately one week (after excluding first and last partial days, remaining days per participant: minimum = 3 days, maximum = 16 days, median = 8 days, mean = 8.43 days, standard deviation = 1.62 days).

After the data collection week, participants had another video call with the researcher. During this meeting participants first uninstalled the App from their phones. They then were sent a link to complete a battery of questionnaires via Qualtrics. The questionnaires included measures of mental health, behavioural activation and inhibition, attentional control and habits.

To maximize quality of questionnaire answers and minimize likelihood of low-effort or inattentive responding (34), we included quality and attention checks before, during and after questionnaire completion. The quality checks before completion included the requirements to write two sentences in full English about their favorite book or film at the start, as well as asking participants to commit to providing thoughtful answers at the beginning of the survey, with the question, 'We care about the quality of our survey data. For us to get the most accurate measures, it is important that you provide thoughtful answers to all questions of this survey. Do you commit to providing thoughtful answers to the questions in this survey?' During questionnaire completion, there were three attention checks which consisted of questions in the same format as questionnaire questions but with an obvious correct answer.

These included the questions 'I will often eat rotten food for the enjoyment of it', 'I often spend multiple weeks without eating anything', and 'Please respond with "moderately" to this question.' Finally, after completion, participants were asked, 'We care about the quality of our data. To get the most accurate measures, it is important that we only include data that was provided thoughtfully. Your response to this question will not affect your reimbursement.

Did you provide meaningful/thoughtful answers throughout the survey?'

No participants failed the quality pre-commitment check, two failed the quality postcommitment check, five failed the first attention check, one failed the second attention check and one failed the third attention check. Only one participant failed more than one of these checks (the first and second attention checks), leaving eight participants in total who failed at least one quality or attention check. To establish whether these eight participants with potentially low-quality questionnaire answers affected our results, we repeated analyses for all main results with these participants excluded and report all results both with and without these exclusions.

Questionnaire measures

After the data collection week, a researcher met with participants to first download the Data Collection App and then complete nine questionnaires. This included three mental health questionnaires: the GAD-7 to measure anxiety (20), the PHQ-8 to measure depression (19) and the OCI-R to measure Obsessive Compulsive Disorder tendency (21). Further, participants completed measures of attentional control via the short-form Attentional Control Scale (ACS) (35); short-form 10-item version at the Affective Research Core short-form materials (University of Wisconsin-Madison; https://arc.psych.wisc.edu/self-report/attention-control-scale-attc/))) and behavioural inhibition and activation systems (the Behavioural Inhibition / Behavioural Activation Scale (BIS/BAS)) (36). Lastly, participants completed the Self-Reported Habit Index (SRHI), a twelve-item questionnaire where the self-reported habitual nature of a given activity is reported (37). Participants completed the SRHI four times, where the activity in question was social media, their phone, and the Apps that they selfreported using most and least automatically. To establish these 'most automatic' and 'least automatic' apps for each participant, participants were first asked for a free-text response to the questions, 'Which App on your phone do you use in the most automatic way, rather than for a specific, planned purpose?' and 'Which App on your phone do you use in the least automatic way, and mostly just for a specific, planned purpose?' Their answers to these questions were used as the objects for the respective SRHIs.

Pre-processing

During data pre-processing, we first checked for irregularities in the data. We defined a 'session' as the time between each phone unlocking and locking, and an 'App-session' as the time for which a single app was in the foreground within a session, such that there could be multiple App-sessions for the same App within a session. When examining the data for irregularities, we found that 63 of 482,586 app sessions (0.0001%) were over one hour long, while 575 out of 73,550 phone sessions were over one hour long (0.0078%). Given that these unexpectedly long App-sessions and sessions represented a very small proportion of the data, although it was possible that such long sessions were the results of technical errors in data collection, or participants leaving their phones on while asleep or absent, we chose not to remove any of these App-sessions or sessions during data pre-processing.

We had also installed a 'pause' button in the Data Collection App so that participants were able to pause data collection whenever they wanted. 34 participants used the 'pause' button at least once during the data collection week. Rather than removing all the data for these participants, for the analyses of App-level data (i.e. network analyses), we removed all sessions containing at least one pause (240 sessions out of 73,550 sessions; 0.003%). For analyses in which we calculated means per day (such as, in research question 3, mean time spent per day, and other micro-behaviour variables in the clustering analysis), we removed all days containing at least one pause (78 out of 697 days; 0.112%).

For all analyses relating to the participants' self-reported most and least automatic apps to their objective Data Collection App data (i.e. not for the SRHI for these reported apps), we included only those participants for whom we could identify one unique app which occurred at least once in their data. Table S1 in the Supplementary Information contains a record of how all participant free-text answers were mapped to an underlying App in the Data Collection App data. These exclusions reduced our sample size for these analyses to n = 61.

For the analyses of App position in a phone session (Figure 4d), we excluded all App-sessions where the 'App' was the phone 'homescreen' (i.e., if the first App in a session was the homescreen, then we would consider the 'first App' to be the App after this). The Supplementary Information contains a full list of the underlying names of each of the 'homescreen' Apps excluded.

The appusage2_logs dataset contained 586 unique participants, and after pre-processing excluded 21 participants with less than seven full days of data, we used a final dataset of n = 565. Pre-processing

We pre-processed both the EARS and the YSR data. For the EARS data, initial pre-processing was carried out by the Ksana health team, before making data available in the ABCD release, removing known errors (e.g., Apps that are known to run for 24 hours; duplicative events) and undergoing further cleaning processes. From the original raw datasets, we further preprocessed the EARS data for our analysis.

First, as there was no 'Screen on/off' variable to identify session starts and endings, we needed to infer phone usage sessions (i.e. when a phone was turned on and off) from the dataset, as the App-journey network uses this information to construct network edges (as each represents the conditional probability of visiting the subsequent App during the same phone session). Using the time-stamps of App foreground sessions, we defined the start of a new 'phone session' as when the start time of an app usage session was 5 seconds or more after the end time of the previous app usage session. As the App usage data was collected for three weeks for each participant per session, we further restricted all participants to only their first full seven days of data (e.g. if the first day of data collection does not include a whole 24 hours but the second does, we included seven days from the second day onwards).

This was to ensure comparability with the previous sample who used approximately one week of phone-session data.

We excluded all participants who had fewer than seven days of data after removing the first and last incomplete days (excluding n = 21 out of n = 586, leaving n = 565 remaining), and retained exactly the first seven days of data for the remaining 565 participants. As we consistently retained the first seven days of an approximately three-week collection period, this meant that the gap between the last day of App data collection and the date on which the mental health questionnaires were completed ranged from 7 to 81 days (mean = 9.36 days, median = 7 days, SD = 7.06 days).

For the YSR, we preregistered (22) to analyse three mental health variables, corresponding to DSM criteria for anxiety, depression and Attention-Deficit/Hyperactivity Disorder (ADHD) from the Youth Self Report Questionnaire. In our previous study we looked at anxiety, depression and Obsessive Compulsive Disorder (OCD) (41). However the Youth Self-Report does not contain an OCD measure, so we extended the analysis to ADHD (42). Specifically, we analysed the DSM Anxiety symptoms summary score (mh_y_ysr__dsm__anx_tscore), the Depression symptoms summary score (mh_y_ysr__dsm__dep_tscore) and the ADHD symptoms summary score (mh_y_ysr__dsm__adhd_tscore).

Network analysis

The R package igraph (version 2.1.4) was used to conduct network analyses (44). Specifically, a network was constructed for each participant wherein all Apps which appeared at least once in their data represented 'nodes', and the weight of the edge between App A and App B was the conditional probability that App B was used after App A in a session, given that App A was used in a session. This was calculated as the number of times that App B was visited after App A in a session, divided by the number of sessions in which App A appeared at least once.

We defined modularity using the 'Louvain' algorithm in igraph (44). The Louvain algorithm calculates the modularity of undirected graphs, therefore we used the function 'as.undirected' to convert each graph before use. This function turns a directed graph to an undirected graph by adding the weights of edges in each direction to take the sum of all directed weights as the single undirected weight. We defined density using the 'edge_density' function.

The node-level properties we measured included in-strength, out-strength, in-diversity, outdiversity, eigenvector centrality and coreness. In-and out-strength were calculated using the function 'strength' in igraph for each node. In-and out-diversity were calculated by quantifying the Shannon entropy across in-or out-weights, respectively for each node, and were set to 0 in the case where there was just one edge. Eigenvector centrality and coreness were calculated using the 'eigen_centrality' and 'coreness' igraph functions.
