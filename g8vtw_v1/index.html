Meta-scientific research has shown nonsignificant p values are commonly misinterpreted. It is incorrect to infer that there is ‘no effect’, ‘no difference’, or that groups are ‘the same’ after p > 0.05.

It is possible that there is a true non-zero effect, but that the study did not detect it. Make sure your inference acknowledges that it is possible that there is a non-zero effect. It is correct to include the effect is ‘not significantly’ different, although this just restates that p > 0.05.

This module searches for statements of ethics approval, IRB approval, institutional review board approval, and related terms.

How Power Analysis Check works

This module uses regular expressions to identify sentences that contain a statistical power analysis. If specified by the user, it also uses a large language model (LLM) to extract information reported in power analyses, including the statistical test, sample size, alpha level, desired level of power, and magnitude and type of effect size.

The Power Analysis Check module uses regular expressions to identify sentences that contain a statistical power analysis. Without the use of an LLM, the module uses regular expressions to classify the power analysis as a-priori, sensitivity or post-hoc. With the use of an LLM, it checks if the power analysis is reported with all required information.

The regular expressions can miss power analyses, or fail to classify them correctly. The type of power analysis is often difficult to classify, which can easily be solved by explicitly specifying the type of power analysis as ‘a-priori’, ‘sensitivity’, or ‘post-hoc’. Note that ‘post-hoc’ or ‘observed’ power is rarely useful. The LLM can fail to identify information in the paper, and will not have access to information in paragraphs in the paper other than those that contain the word ‘power’. This package was validated by the Metacheck team on articles in Psychological Science.

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

This module uses regular expressions to identify p-values. It will flag any values reported as p > ? or p < numbers greater than .001. It will also flag p-values reported as exactly zero (e.g., p = .000, p = 0.00), which are mathematically impossible — p-values are never exactly zero and should instead be reported as p < .001.

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). GROBID often puts such notes into the running text, so each p-value is judged by the words in its own clause (the text up to a “;” or a full stop), and never left out when a test statistic belongs to it (“F(1, 7) = 8.03, # p < .05”). The column not_a_test of the table says why a p-value was left out (“marker”, “threshold” or “legend”). Notes in other forms, such as a marker after the p-value (“p < .05 (*)“), are still flagged.

This module sometimes flags false positives when sentences discuss how p-value thresholds were set. It can also miss an imprecise p-value that is reported against a threshold (“decreased at the p < .05 significance threshold”).

This module only checks p-values reported in the running text of the manuscript. It cannot (yet) process p-values reported only in tables (as opposed to a table’s footnote text, which the module does see and tries to exclude — see above).

This module was developed by Lisa DeBruine and Daniel Lakens

How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Background: Over 17% of children live with a chronic somatic illness and are at increased risk of experiencing psychological problems, such as anxiety and depression. Grow It! is a transdiagnostic mobile health (mHealth) intervention that combines experience sampling and personalised mood feedback with daily coping challenges to promote reflection, emotional insight and adaptive coping. The app fosters a collaborative team experience in which participants contribute to growing a shared virtual tree and communicate through a chat function with predesigned stickers.

Objective: This study aimed to evaluate the acceptability of the Grow It! app among adolescents with a chronic somatic illness and to identify key lessons the development of other gamified mHealth apps designed to promote well-being.

Methods: This preregistered study is part of a randomised waitlist controlled trial.

Adolescents with a chronic somatic illness aged 10-18 years old were recruited from a university medical children's hospital. Upon inclusion, adolescents were randomised to an intervention group that used the Grow It! app or a waitlist control group. Follow up questionnaires were completed immediately after the four week intervention period and three months later. Consecutively, the waitlist control group was also offered the Grow It! app and completed questionnaires immediately after use and three months later. Participants completed user experience survey comprising open ended and closed questions after playing the app. Responses were analysed using qualitative content analysis and descriptive statistics.

Results: Between August 2021 and September 2023, 208 adolescents were included in the study. Due to participant attrition, the user experience survey was distributed to 183 participants and completed by 150 (Mage=13.95, 39.33% male, 59.33% female, 1.33% other).

The app received a mean overall rating of 7.32 out of 10, and a mean look-and-feel rating of 7.98 out of 10; 84% would recommend the app to a friend. Participants reported that the app helped them recognise their emotions and gain greater self-insight. They also described its design as colourful and visually appealing. Suggested improvements included adjusting the timing and frequency of the momentary assessments, and expanding the chat function to allow free-text messages or a wider selection of stickers.

The Grow It! app is well-accepted by adolescents aged 10 to 18 with a chronic somatic illness, although optimising the chat function and reducing questionnaire burden may further improve user experience. Combined with evidence of effectiveness, these findings on acceptability and user experience support the implementation of the Grow It! app in paediatric healthcare.

Introduction

Over 17% of children live with a chronic somatic illness [1], such as congenital heart diseases, asthma or eczema. A chronic illness is defined as a condition that lasts longer than three months, recurs more than three times a year and/or is related to long-term use of medication, treatment or help [1]. Children with a chronic illness are at increased risk of developing mental health problems, such as a reduced quality of life [2], loneliness [3] and anxiety and depression, both during adolescence [4] and in their adult life [5].

To address these mental health problems, an increasing number of mobile health (mHealth) apps is being developed [6]. Different systematic reviews and meta-analyses show that these mHealth apps are effective at reducing mental health problems [7, 8] and evidence suggests that their effects may be comparable to those achieved with face-to-face interventions [9]. Compared to these more conventional face-to-face treatments, mHealth apps have several advantages such as overcoming stigma-related barriers for accessing mental healthcare [10] and a possible cost-reduction [11]. Although concerns have been raised around engagement and attrition in mHealth apps [12], it remains unclear whether attrition is substantially higher in mHealth compared to traditional face-to-face care, where treatment discontinuation is also common [13].

A potential solution to increase engagement, is to gamify the mHealth apps [14, 15].

Gamification has been defined as incorporating game design elements into non-game contexts [16], such as mHealth apps. Gamification has been shown to increase user engagement with mobile apps [17], improve data quality and quantity [18], and possibly lead to behaviour change [19]. However, little research exists on how gamification affects user experience and acceptability in youth with a chronic illness.

An example of a recent gamified mHealth app is the Grow It! app [20]. The Grow It! app is designed to promote mental well-being in youth aged 10 to 25 years old. The app targets three working mechanisms: 1) emotional awareness, through daily emotion diary questionnaires using the Experience Sampling Method (ESM), 2) emotion reflection, through a personalised mood profile reflecting the ESM outcomes, and 3) enhancing adaptive coping, through daily challenges based on Cognitive Behavioural Therapy (CBT). ESM is a method where participants report on their thoughts, feelings, symptoms and/or behaviour in their daily life [21, 22], typically during multiple (random) times per day for several days or weeks [23]. In terms of gamification elements, the app focuses on cooperation and competition.

Adolescents participate in teams of eight players, where they compete against other teams to decorate and grow their shared virtual tree.

In a series of pre-post studies among 3153 adolescents from the general population, the majority of adolescents showed an improvement in affective and cognitive well-being after playing the Grow It! app for three or six weeks [24]. A substantial proportion of adolescents also self-reported that the app helped them be aware of their feelings and helped improve self-insight [25]. We then adapted the content of the Grow It! app together with adolescents with a chronic illness and healthcare professionals. A Randomised Controlled Trial (RCT) on 208 adolescents with a chronic illness showed an added benefit of the Grow It! app for adolescents with heightened symptoms of anxiety or depression [26]. However, no results are available regarding the acceptability of the Grow It! app among adolescents with a chronic illness. Assessing these factors is crucial to understand the app's potential for implementation in paediatric healthcare and whether it meets the needs and preferences of adolescents with a chronic somatic illness.

The current paper describes the acceptability and appropriateness of the Grow It! app to adolescents aged 10 to 18 with a chronic illness, after using the Grow It! app for four weeks. Data from the aforementioned RCT on 208 adolescents were used [26]. For this study, we follow the definitions proposed by Proctor et al. [27] who defined acceptability as: "the perception among implementation stakeholders that a given treatment, service, practice or innovation is agreeable, palatable or satisfactory." and appropriateness as: "the perceived fit, relevance or compatibility of the innovation or evidence based practice for a given practice setting, provider or consumer; and/or perceived fit of the innovation to address a particular issue or problem".

The following preregistered research questions were formulated: 1a. What is the acceptability of the overall look and feel of the Grow It! app? 1b. Is the acceptability of the overall look and feel different depending on age or gender of the child? 2. What is the acceptability of the psychological working mechanisms (i.e., ESM, mood profile and challenges)?

3. What are adolescents' wants and needs for further development?

The Grow It! app

The Grow It! app is a multiplayer mHealth app designed to promote mental wellbeing, see also Figure 2. Participants used the app for four weeks on their smartphone or, in two instances, on a smartphone provided by the study team. The Grow It! app addresses three working mechanisms: emotional awareness, emotion reflection and enhancing adaptive coping. A detailed explanation of the Grow It! app and its design is available in Dietvorst et al. [20].

Emotional awareness was targeted through ESM questionnaires. These short 1-minute questionnaires were sent five times each day in the Grow It! app, at random time intervals (i.e., signal-contingent schedule with random prompts that participants receive as a push message on their phone). Questions were related to current whereabouts, activity and company, as well as sleep, pain levels and negative and positive affect.

Emotion reflection is targeted using a mood profile, displaying the real-time results from the ESM questionnaires [29]. Each emotion was shown as a circle varying in size, depending on the reported intensity of the emotion. The mood profile could be filtered using the time period (i.e., day, week or study duration), the company kept and the situation the participant was in while completing the ESM.

Adaptive coping was targeted through a daily challenge aimed at several coping strategies, including distraction, problem solving, social support and acceptance. For the challenges, participants were offered a daily selection of three coping-based challenges, of which they could choose one. An example would be complimenting a friend or asking a friend what they like about you.

Teams in the app consisted of eight anonymous players, with each person in the team collecting points to grow their shared virtual tree. Points could be earned by completing ESM questionnaires or a daily challenge. Team members could communicate using emojis within a build-in chat function. Measures Participants provided their gender and date of birth upon study inclusion. An online survey was created to measure acceptability and appropriateness of the Grow It! app. Rather than focussing on specific implementation outcomes, the survey focussed on the overall experience and experience of different components of the app. The survey contained three sections, which map onto our three research questions: 1) Overall rating of the app and look and feel, 2) rating of the psychological working mechanisms (evaluation of ESM, evaluation of challenges in the app, evaluation of the mood profile), and What grade would you rate the appearance of the app?"). The survey consisted of 24 questions. The full (translated) version is available in the preregistration [28].

Preregistered statistical analyses

Quantitative data were summarised using descriptive statistics. Means and standard deviations were calculated for all quantitative data. Hierarchical regression analyses were conducted to assess whether age, gender and medical diagnoses were related to the overall grade of the app and the grade of the look and feel. To assess significance of these two-sided tests, p-values were compared to α = .05. Multiple testing was corrected for using the procedure for False Discovery Rates (FDR) described by Benjamini and Hochberg [30].

Qualitative data were analysed using inductive content analysis on a manifest level.

First, the survey responses were read by two researchers (MvD and a research assistant), after which initial codes were developed independently by the two researchers based on 25 surveys. In a first consensus meeting, the codes were discussed and code sheets were developed. The code sheets were used by the researchers to code the first 25 surveys, after which they were discussed in a consensus meeting. The intercoder-reliability was 89.47%.

After this each researcher coded half of the remaining data. All data analysis scripts and raw output are available on the OSF [31].

Psychological working mechanisms

Research question 2 focused on the acceptability of the psychological working mechanisms in the Grow It! app. The first psychological working mechanism was emotional awareness, targeted through ESM mood questionnaires. These were sent out five times a day.

The majority of participants (69.33%) reported that these questions had some effect on them.

On a multiple choice question, the most often reported effect of the ESM questions was thinking about how participants felt (46.67%) or getting to know oneself better (26.67%). A minority (6.67%) reported that the questions made them feel better. At the same time, the frequency of the questions was perceived as too high by about half of the participants (51.33%).

The second working mechanism was reflection on emotions, targeted through the mood profile. This mood profile provided feedback to the participants, based on their answers to the ESM questions. Most participants thought the way information was displayed in the mood profile was very clear (35.33%) or totally clear (24%). About half of the participants (49.33%) indicated that the mood profile had an effect on them, such as making them think about how they feel more often (26.67%) or getting to know themselves better (18.67%). The other half of the participants (50.67%) felt they were not affected by the mood profile. About a quarter of the participants (22%) indicated that they shared their mood profile with others (e.g., parents, teachers or healthcare professionals).

The third psychological working mechanism was adaptive coping, targeted through CBT-based challenges. The majority of the participants (55.33%) thought this had no effect on them. For the participants that did indicate an effect, they most often reported that they were more physically active (15.33%) or that they were better at accepting situations (14%).

Discussion

This study investigated the acceptability of the Grow It! app, a multiplayer mHealth app that aims to promote mental well-being, through emotional awareness, reflection on emotions and adaptive coping [20]. In a series of iterations with game-designers, youth and healthcare professionals, this app was developed to meet the unique needs of adolescents with a chronic somatic illness. A total of 150 Dutch youth aged 10 to 18 with a chronic illness played the Grow It! app for four weeks and completed a user experience survey. This provided us with the first insights into the acceptability of the overall look and feel, the acceptability of the psychological working mechanisms and adolescents´ wants and needs for further development.

Acceptability of look and feel

Results showed that the Grow It! app was acceptable in terms of overall rating and look and feel. More specifically, a total of 84% would recommend the app to their friends, which is 10% higher than results on Grow It! in the general population [20]. The overall acceptability of the app did not depend on the participants' age or gender, while the appearance was rated somewhat higher by girls. This suggests that the app can be widely implemented, but that the design and appearance could be improved for boys. Combined with evidence for effectiveness, the app is recommended for adolescents with mild psychological complaints [26].

Despite good ratings of the overall look and feel, almost half of the participants thought the app did not help them or did little to help them. This is also corroborated in the quantitative findings described in the main outcome paper of the study [26], where we did not find an overall group effect of the Grow It! app when compared to a waitlist control group.

Instead, results in that paper highlighted that the app may be especially effective for adolescents with pre-existing symptoms of anxiety and depression. These results may in part be explained by the sample selection. All participants received high-quality care and (psychosocial) support from the hospital, leading to a sample with very little symptoms of anxiety and depression.

In addition, participants may be differentially impacted by their medical diagnosis. For instance, participants with a cleft will typically visit the hospital every few years, possibly leading to a lesser impact of their medical diagnosis.

Teams were created to increase competition and enhance learning [32]. In this study, the team aspect of the game was appreciated by participants when asked broadly about their overall experience. However, follow-up questions highlighted that the way of communicating with the team (i.e., through a closed chat using stickers only) was not rated as well as the overall team experience. In addition, many of the suggested changes related to the chat function. The Grow It! app does not allow free input of text in the chat due to privacy and safety concerns. This seems to contradict the needs and wants of youth, of whom some indicated they wanted an open chat or wanted more stickers, highlighting an important tradeoff between facilitating contact, while taking privacy and safety concerns into account.

Acceptability of working mechanisms

The app seemed appropriate to use and seemed to help participants in recognising their emotions or helping to get to know themselves better. This could be due to the regular ESM questions and the feedback provided with the mood profile. In in-depth interviews with participants of the Grow It! study, their parents and healthcare professionals also showed that the app fostered emotional awareness and early recognition of emotional difficulties [33].

Other studies have shown that completing ESM questions can lower depressive symptoms [34] and that participants may adjust their mood based on feedback using ESM outcomes [35].

The mood profile provided a real-time overview of the participants' current and past mood. This psychological working mechanism was perceived as clear, with about half of the participants reporting some effect of the mood profile, such as recognising their emotions better or getting to know themselves better. However, despite the current results, results from Grow It! in the general population show that adding the mood profile did not change the overall compliance nor did it improve psychological outcomes [29]. In addition, the overall rating for the app in the general population also remained unchanged after introducing the mood profile in the app. It remains unclear how the mood profile in its current form contributes to changes in mental well-being.

Similar to the mood profile, about half of the participants did not think the challenges had an effect on them. Interestingly, the challenges were not named by participants as something that needed to be changed about the Grow It! app. Although CBT has been proven to be an effective element of mHealth apps [15], the challenges in its current form do not seem to be related to mental health outcomes when measured both qualitatively and quantitatively [26].

It is possible that the goal of the challenges is unclear to participants. The app does not contain an explanation of why participants should do the challenges, or what coping technique the challenges target. Including psychoeducational feedback on coping can potentially improve participant experience and app effectiveness [6].

Some participants were motivated by intrinsic factors, such as wanting to test a new app, but the majority were motivated by extrinsic factors, such as the possibility of winning a prize. Clearly, participants' motivation for taking part in research differs from the motivation of patients in an outpatient hospital clinic. This is especially important when implementing mHealth apps [36], as research results may not translate directly into clinical practice.

Professionals developing or working with mHealth apps should take this difference into account, by also conducting real-world implementation studies [36, 37].

Next steps for Grow It! development

Participants provided many helpful suggestions for next design iterations. Suggestions for improvements were primarily related to the ESM questionnaires. In research settings, participants are typically given multiple-item questionnaires multiple times per day [21]. At the same time, these questionnaires may increase participant burden [38]. Although we used gamification elements where participants could earn points for completing the questionnaires, the sampling scheme was not personalised or tailored to participants' schedules, possibly influencing their motivation and compliance. For instance, participants wanted a different timing or a longer time window during which they could complete the ESM questionnaires.

As such, as next development step could include more tailoring options for participants by adding their own questions or providing the possibility of changing the ESM schedule.

Another next step is to focus on the multiplayer experience. Although participants quite liked to play in a team, the chat function was suboptimal. Data on Grow It! from the general population also showed that the team element can be experienced as frustrating when other team members are not actively earning points towards the team tree [25]. From an implementation perspective, team-based participation is less feasible as eight participants must register for the Grow It! app before the team can start. This creates a waiting period between registration and participation. Therefore, another development step is to change the multiplayer experience. Players will play individually and grow their own tree, and are able to see other players' trees in order to feel part of a community and are motivated to grow their tree. To maintain the social experience, players will be able to send predefined supportive messages to other players.

Strengths and limitations

This study assessed the acceptability of one of the first mHealth apps for youth with a chronic illness. A strength of this study is that both quantitative and qualitative data were combined to study acceptability. Second, we were able to include a sample with a wide age range and representative gender distribution. One specific challenge we encountered, was measuring mental well-being during school hours, as not all participants were allowed to use their phone during school hours. This highlights an important conflict between obtaining ecologically valid measurements for researchers on the one hand and feasibility for the participants on the other hand. The feasibility for participants can be improved, for instance, by providing them with letters for their school, detailing why the school should allow the participant to use their phone during the intervention period. Another option for implementation in clinical practice would be to personalise the sampling schemes to better tailor towards adolescent's specific time schedules and preferences [e.g., 39].

Another limitation is that a selection bias may have influenced the results.

Approximately 20% of participants randomised into the study did not complete the user experience survey. Participants who stopped using the app prematurely may have been less likely to complete the user experience survey, potentially resulting in their experiences being underrepresented in the findings.

In addition, youth who were less inclined to use mHealth apps may have been less likely to participate in the study in the first place. However, it is unclear to what extent this bias would generalise to a healthcare setting. It is possible that mHealth apps do not appeal to all adolescents for reasons that are not necessarily related to the quality or acceptability of the app itself. For example, some youth may prefer face-to-face contact over using digital applications altogether [40] and may thus refrain from using mHealth apps such as Grow It!.

Conclusions

In conclusion, results showed that the Grow It! app was acceptable to youth with a chronic somatic illness. Participants appreciated the look and feel, and psychological working mechanisms. However, important considerations remain. For instance, the ESM questionnaires could be more personalised toward adolescents' needs, psychoeducation can be included to explain the purpose of the psychological working mechanisms and the social experience of the app can be improved. Combined with evidence of effectiveness [26], we learned that it is acceptable, appropriate and potentially effective to use the Grow It! app in paediatric healthcare. However, real-world studies should be conducted to understand how Grow It! can be successfully implemented into paediatric healthcare.
