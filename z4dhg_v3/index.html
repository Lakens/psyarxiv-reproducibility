This module searches for statements of ethics approval, IRB approval, institutional review board approval, and related terms.

Patterns are designed to capture:

Animal research committee names - Institutional Animal Care and Use Committee / IACUC (US standard) - Any sentence containing animal(s) and committee (or board/panel) within ~5 words of each other — catches Experimental Animal Care and Use Committee, Animal Ethics Committee, Animal Welfare Board, Animal Welfare Ethical Review Body, etc. - UK: Animal Welfare Ethical Review Body / AWERB - Dutch: Dierexperimentencommissie / DEC (see DEC constraint above); Instantie voor Dierenwelzijn / IvD - German: Tierversuchskommission / TvK (advisory committee under §15 Tierschutzgesetz) - French: Comité d'éthique en expérimentation animale / CEEA; Comité d'éthique animale - Spanish: Comité de ética en experimentación animal / CEEA

Declaration of Helsinki - Declaration of Helsinki / Helsinki Declaration

How Exact P-Values works

List any p-values reported with insufficient precision (e.g., p < .05 or p = n.s.) or reported as exactly zero (e.g., p = .000).

A p-value that is not the result of a test is not flagged: a table note (“* p < .05, ** p < .01”), a figure legend (“Asterisks indicate significant differences (p < .05)”, “Values in bold are significant at p < .05”) or a stated threshold (“p < .05 was considered significant”, “thresholded at p < .001”). How Code Check works

This module retrieves information from repositories checked by repo_check about code files (R, Python, SAS, SPSS, Stata, Mplus, MATLAB).

The Code Check module checks R (also R Markdown and Quarto), Python (also Jupyter notebooks), SAS, SPSS, Stata, Mplus, and MATLAB files, using regular expressions to check the code; JASP files are listed but not read. The language of a Quarto document or a notebook is read from the file itself (its engine or kernel), not from its extension. The regular expression search will detect the number of comments, the lines at which libraries/imports are loaded, attempts to detect absolute paths to files, setwd() and install.packages() calls, and lists files that are loaded, and checks if these files are in the repository; R code is also parsed. The module will return suggestions to improve the code if there are no comments, if libraries/imports are loaded in lines further than 4 lines apart, if files that are loaded are not in the repository, if absolute file paths, setwd() or install.packages() are found, and if R code cannot be parsed.

The regular expressions can miss information in code files, or falsely detect parts of the code as a fixed file path. Libraries/imports might be loaded in one block, even if there are more than 3 intermittent lines. The module was tried out internally on papers published in Psychological Science, but has not been formally validated. There might be valid reasons why some loaded files can’t be shared, but the module can’t evaluate these reasons, and always gives a warning.

The module also checks whether the repository pins the R/package versions the analysis actually depended on: an renv.lock file (parsed for the R version and every locked package + its version/source), a sessionInfo()/sessioninfo::session_info() text dump (matched by filename — sessionInfo.txt/session_info.txt and similar, or embedded in a README), or a groundhog::groundhog.library()/checkpoint::checkpoint() date-pin call in the code (a bare library(groundhog)/library(checkpoint) does not count — the pinning call itself must be present). How Data Check works

This module classifies the files in a repository into semantic types (data, codebook, code, software, output, supplemental, readme, asset, other) and, for tabular data files, extracts each column’s type and summary statistics.

The Data Check module consumes the file list produced by repo_check (or any files added via local_path). Each file is classified with rule-based heuristics layered over metacheck’s file_category() and file_types: file names matching README / codebook patterns win first, then an extension crosswalk, then format-locked extension overrides. For every file classified as tabular data that is available locally, the module reads the file head, describes each column with data_col_facets() and computes summary statistics for numeric columns. Every sheet of a spreadsheet that holds a table is read: a file with several such sheets has its columns under source_file = "file.xlsx [sheet]", and the sheet column names the sheet of any spreadsheet with several sheets; a sheet of notes or a codebook is treated as documentation when the file has another table. Following DDI, a column is described by orthogonal facets rather than a single type: representation (numeric/text/datetime/code — how it is stored), measurement_level (Stevens: nominal/ordinal/interval/ratio), concept (what it measures: reaction_time/age/gender/likert/id/…), role (identifier/measure/condition/timestamp), unit, and a quality state (ok/empty/constant). Concepts are detected by name+value rules (the demographic concepts via data_check_demographic()); when llm_use(TRUE) the model fills concepts and measurement levels the rules left blank. Qualtrics survey exports are recognised (data_check_is_qualtrics()): their extra header rows are stripped so columns type correctly, and the reserved response-metadata columns (StartDate, Duration, Finished, …) are tagged.

The module defaults to rules-only when llm_use(FALSE): columns the rules cannot resolve (ambiguous 3–20-unique integers, ambiguous character columns) fall back to continuous / text respectively. When llm_use(TRUE), ambiguous columns and unresolved file types (other) are sent to llm() for optional refinement, and every file is assigned a study group (ex1, pilot2, shared, …) so that multi-study repositories can be recognised (used by psychds_check). Without an LLM the study group is left NA (unknown).

Column extraction requires files to be readable from disk. Files fetched by repo_check from OSF/GitHub/etc. without a local copy (file_location is NA) are classified but not column-extracted; pass local_path to point at a downloaded copy of the repository.

For a paper whose repository is on Dryad, this means column extraction never happens unless a Dryad API key is set: Dryad requires one to download file bytes, even from a fully public dataset (dataset listing and metadata do not need one). Without a key, every Dryad file stays classified but un-downloaded, column_n is 0, and a warning naming Dryad and ?dryad_pat/?dryad_auth is included among the download failures. A one-time session message is also shown (see repo_check) the first time a Dryad dataset is encountered with no key set.

Every downloaded text file the authors wrote (code, settings, survey definitions such as Qualtrics .qsf files, documentation, outputs) is searched for keys: API keys, access tokens and private keys, which let anyone who downloads the file use a paid service at the authors’ cost. Of a tabular data file only the column names and first 3 rows of the table as read are searched: its values come from participants, but a key the authors set for a whole survey (as embedded data in a Qualtrics survey flow) is exported in every response. The search uses the rules of the secret scanner betterleaks (https://github.com/betterleaks/betterleaks, MIT licence) of high and medium confidence. A key found turns the traffic light red; the report and the keys table give its file, line and type, and only its beginning. Other files over 25 MB and binary files are not searched. A key is never tested with its provider. Every module’s result has any whole key replaced by “keyremoved” (see module_run()).

How Reproducibility Check works

This module assesses whether a paper’s R and Python code can be run on its data. It works in two phases. The static phase (always run) collects the package dependencies the code declares, rewrites the data-file paths that do not work in the repository as the authors organised it, works out the order the scripts must run in, and diagnoses why any referenced input file is unavailable — reporting what a reproduction attempt would involve and where it is likely to break. The execution phase (opt-in, execute = TRUE) then actually runs the code: it copies the repository into a throwaway directory, optionally installs the declared dependencies into a throwaway library, runs each script in order in an isolated subprocess with a per-script timeout, and captures the outcome and full output of each run.

By default (execute = FALSE) the module does not run any code — it performs only static analysis: reading dependencies with the same extractors as code_check, finding the files the code references in the repository, and building a run-order dependency graph. It reports what would be installed and run rather than doing it.

When execute = TRUE, the module additionally runs the downloaded code on your machine — a deliberate, opt-in action gated behind that argument (callr is required for R code). Each script runs in an isolated subprocess so a crash cannot take down the R session; note this isolates crashes, not the filesystem or network. Installs (when install_missing = TRUE) and the throwaway run library never touch your main R library. Each script’s outcome is one of ran_ok, errored, timed_out, dependency_unavailable, not_parsed, run_by_source (an R script another script runs with source(), which is run only inside that script, since on its own it lacks the packages and objects the sourcing script sets up first), run_by_import (a Python file other files import, a module rather than a script, unless it has an if __name__ == "__main__": block), jags_model (a JAGS or BUGS model saved with an R extension, which another script reads) or not_r_content (a file that is not R at all, such as a JSON or HTML dump); these last two are not run and are not failures. python2 marks Python 2 code that was not run. With sandbox = "docker" such code runs with Python 2.7 (option metacheck.docker_image_py2; FALSE turns this off), which modifications records; it is never converted, since that can change results. defines_functions is a file that only defines functions, which is used, not run (table$used_by names the scripts that use it), and not_analysis is a file of software rather than of the analysis: a package’s code, tests, documentation or setup.py, a copy of a tool, a web application, a script a program wrote (table$not_analysis_why says which); neither is run or counted as a script. docker_failed means the container never started, which says nothing about the script, so it keeps the light from being green but does not make it red. needs_a_person is a script that stopped because it asks a person to choose a file or answer a question, or that starts an app, and needs_internet one that stopped because the network is off in a Docker run, or, with internet = TRUE, could not reach what it asked for; download_too_large is a script stopped for downloading more than the limits allow (see internet), and out_of_memory one that, or a program it started (such as a compiler), ran out of the memory each script may use. All four are treated the same way. not_downloaded is a script that stopped on a file the repository lists but that was not downloaded, such as one over max_file_size: it could not be tried, so it is not counted as a script that did not reproduce (summary_table$repro_not_downloaded_n counts them apart). not_read is a file metacheck could not read, so it was not run; the light is then not green, as the file may read and run on another computer, and table$error_message says why, naming a package that is installed but cannot be loaded on the computer that ran the check. empty is a file with nothing in it, which is not run or counted as a script. For a script that did not run through, table$error_message is its error, short (at most 300 characters): the error line of its output, which names a package that is not there, with the address it asked for when it needed the internet, or the time limit it reached; table$reason sorts it into a kind. A timeout means “still running at the cutoff”, not a failure, so raise timeout for legitimately long-running (e.g. Bayesian) scripts. dependency_unavailable means the script’s own package could not be installed from live CRAN, the CRAN Archive, or a named GitHub/URL source — an infrastructure limitation, not a defect in the paper’s code, so unlike errored/timed_out it does not force the traffic light red. The full stdout/stderr of every run is kept in the result’s run_results (the report shows it in per-script dropdowns, capped for readability). The traffic light reflects the STATIC readiness signals by default, but an execution error (errored/timed_out) does recolour it to red — a script that crashes on its own analysis is a genuine reproduction failure. A script that fails with could not find function is run once more with the library() calls the project’s other scripts make added at its top (or the one package that exports the function, or magrittr for %>%), and a script that then runs is reported as reproducible only after that repair.

Dependencies are reported name-only, with the source (CRAN, GitHub, or a base package already shipped with R) — static analysis of the code cannot know which version was used, and running against current package versions is itself informative: a break argues the authors should have pinned versions. When the repository does record versions, a run with recorded_versions = TRUE installs the packages the scripts load at those versions, but it does not change the R version, which remains a limitation of the check.

Run order is derived from read-after-write data dependencies (a script writing a file another reads must run first), source() edges, and numeric filename prefixes as a weak tie-breaker. Ambiguous orderings, dependency cycles, and inputs a script reads but that no earlier script produces (and that are not in the repository) are surfaced as warnings, since these are the situations most likely to make an otherwise-correct reproduction fail.

Python code (.py files, and notebooks and Quarto documents whose code is Python, from which the code is extracted first) goes through the same two phases, reported in its own “Python code” section. Each file is checked for syntax errors with Python’s own parser when a Python interpreter (python, or else python3) is available; dependencies are read from the import statements, with versions from a requirements.txt or pyproject.toml when there is one, and installed with pip; each script runs as its own python process (processx is required), so unlike R scripts, a name one script defines is not available to another. When no Python interpreter is available, the Python files are reported as not run and the R results are still returned. Statistics the Python scripts print are compared with the paper together with the R output and any self-reproducible output (JASP/jamovi, SPSS-Viewer, notebook outputs).

Abstract

Reasoning models expose extended verbal sequences, but final-answer scores leave their organization unresolved. Here we identify a cognitive model organism and establish the Hortus Regis Alti (HRA) Protocol, an operational experimental framework joining a frozen language model, controlled input changes, complete native-token records, relational process coding and measurement-failure screening. Five stages provide 377 formal path or stream records from one seven-billion-parameter model, with engineering checks counted separately. Symbolic closure separated from termination; pooled output reduction concealed an item-specific increase; and correct calculations lost their subsequent task roles. Shared-prefix interventions produced different continuations, while seven emptyinsertion replays reproduced their controls exactly. A registered survey of 96 historical templates under new sampling assignments recovered persistent patterns alongside changed endpoints. Stage 5 reproduced four historical paths completely, but all eight tested self-prefix reconstructions diverged from their historical continuations despite restored reconstructed sampling states. Twelve matched restoration-versus-seed-reset pairs also diverged despite identical first-step model scores. Exact recovery thus defines an observed set of successful preparations, whose general boundary remains to be established. The protocol makes both recovery and failure experimentally revisitable, supporting iterative target discovery and testing with explicit specifications for sequence identity, maintained task relations and terminal outcomes.

[div-01]

A final answer compresses a history of problem solving into a terminal product. The same answer can follow a stable conditional calculation, a substituted problem, or a correct label attached to an incompatible explanation. A wrong answer can follow the absence of a useful calculation, its subsequent loss, or failure to express an otherwise preserved decision. These histories pose different questions. Which representation organized the next inference? When did a calculated relation become a premise? What happened after the stream announced that the problem was solved? Answering these questions requires a preparation that preserves the process at the scale where these distinctions arise.

We adopt a computational, information-processing conception of cognition: transformations of representations and their use in task-directed control. Neisser placed information transformation, storage, recovery and use at the centre of cognitive inquiry; Newell and Simon advanced an empirical account of intelligent action through physical symbol systems; Marr distinguished computational goals, representations and algorithms, and physical implementation. 1, 2, 3 These positions provide different resources for studying a controllable artificial system at a specified analytical level. The analytical commitments stated here do not specify biological status as a necessary condition. A restriction of cognition to humans adds a premise that must be stated separately. We do not adjudicate that premise; a nonbiological system is not excluded from candidacy solely by its substrate. Verbal-report methodology likewise distinguishes accessible report content from the complete processes producing it. 4 We use cognitive model organism (CMO) for the research carrier: a specified model and execution preparation in which selected processing relations can be elicited, recorded, compared and manipulated. Hortus Regis Alti (HRA) names the unfolding cognitive stream under investigation. Chain of thought (CoT) supplies readable symbolic material. The observation plane comprises native token identities, decoded text, boundaries and task-relative relations. We examine a representation through the conditions, referents and later uses assigned to an expression. Dispensing with a psychometric latent-trait model does not dispense with a measurement model: event rules define the readout, while process models propose how the measured relations arise and change.

The components have important precedents. Machine psychology studies models beyond benchmark performance; Thoughtology describes reconstruction and rumination in DeepSeek-R1 traces. 5, 6 Thought Anchors combines sentence resampling and continuation with attention-level analysis; subthought continuation, faithfulness perturbations, token-budget instructions and model-organism studies of associative learning provide related experimental resources. 7, 8, 9, 10, 11 HRA organizes these opportunities into a cumulative research workflow: freeze a specimen, preserve its complete symbolic history, locate a task relation, prepare a controlled continuation, and examine both the response and the instrument's failure modes. The contribution is this operational connection, rather than a claim to have first observed long reasoning or first edited a reasoning trace.

The study developed through successive questions (Fig. 1). Baseline executions exposed reopened reasoning and separated closure from termination. Stage 1 varied restrictive resource descriptions and evaluation criteria; Stage 2 varied allowances, criterion wording and arithmetic coupling. Stage 3 introduced fixed-prefix interventions and a joint four-question context. Stage 4 registered a sample of historical execution templates for new runs under varied seeds and temperatures. The first three stages were exploratory. The fourth fixed its sampling and execution procedure before the included runs. Unexpected exact replays motivated Stage 5, which registered comparisons of from-start regeneration, prefix reconstruction and samplingstate initialization to investigate recovery conditions. This chronology makes unexpected observations part of the method's development rather than retrospective predictions.

A preserved process collection

Stages 1 and 2 contain 72 and 104 trajectories, respectively, with 2,205,963 generated tokens.

The four items are reading configurations of one Bayesian decision problem. At the standard measurement cost, the oracle actions are BUY, BUY, Y1 and Y0; changing the actual cost changes the relevant oracle. Closure, consumption and task relations separate

Symbolic closure and execution termination have distinct native markers. Stage 1 baseline Q1 first emitted </think> at generated token 6,982, continued for another 20,478 tokens before its second closure, and ended at token 27,492. In attempts4 Q4, closure at token 7,532 preceded 25,236 further tokens and a capped ending (Fig. 2a). An announced boundary therefore did not reliably end processing. Across Stages 1-2, 138/176 trajectories reached natural EOS, 83 satisfied the strict action format and 44 satisfied both format and oracle action. These readouts describe different events.

Pooling also concealed opposing paths. Under the Stage 1 1K-budget instruction, total output was 25,921 tokens, 37.4% of the same-stage 32K baseline. Aggregates remain legitimate consumption measures, but they do not identify the path responsible for a change, and capped paths supply censored lengths. This is descriptive: random reordering of the observed values with ties yields an expectation of 35.67/40, and exchangeable continuous ranks yield 36.67/40. The evidential contrast is the inspectable divergence beneath the aggregate, not an excess count of nonmonotonic series.

Shared histories support divergent continuations

Stage 3 supplied controlled continuations of frozen native-token prefixes. Three of three first-action replays and four of four fixed-point replays matched their controls exactly over 1,563 and 15,021 continuation tokens, respectively, including finish reason.

Insertion length alone did not determine the response (Fig. 3). At the fixed point, arithmetic verification and error assertion each occupied 15 inserted tokens. Arithmetic verification produced 3,710, 9,290, 8,740 and 7,410 continuation tokens, with no immediate thinking closure.

Exact recovery has an empirical boundary

Directed reading of all 28 new outputs localized 377 evidence passages. Repeated decisiondoubt-reopening on the same referent was observed in 15/28 paths, with two unresolved; explicit, valid detection of a task-condition or role mismatch occurred in 14/28. Seven paths contained both. Detection did not guarantee maintained correction. S5-010 identified that Birch reported Y, briefly adopted that relation, then returned to a Z-based relation; later passages repeatedly reopened value comparisons. The two events concerned different referents, so their sequence does not alone establish causation. Donor readings could also persist alongside host evaluation conditions without a verified return to the original task calculation. Of six capped paths, five lacked thinking closure; S5-027 continued for 306 tokens after closure without EOS. Sequence recurrence, relation repair and termination remain distinct readouts.

The probes require their own calibration

Measurement failure was observable in the same material. A 349-token exact cycle in Stage 2 had a distinct-8-gram ratio of .995984 in a final 256-token window but .042517 in an 8,192token window. A locally diverse window missed recurrence at the cycle's scale. Stage 4's wholerecord detector found exact native cycles in 21 trajectories, including two that eventually reached EOS. Repetition, decision reopening and failure to terminate are consequently separate readouts, with the detection window and criterion preserved in each result.

Literal echo and contextual use also separate. Stage 1 budget, attempt and time instructions produced no edited-input 4-gram matches across 48 trajectories, despite differing continuations. Some time-related reasoning was visible without literal reuse. A hit therefore locates a fragment; zero hits do not establish absence of processing. Likewise, a numerical posterior in an enumerated table is not sufficient evidence that the model is maintaining the supplied current readings. These checks make the measurement relation explicit and supply concrete falsepositive and false-negative routes, without discarding the task failures that motivate further study.

Discussion

Endpoint scoring treats reasoning models as black-box oracles; the HRA Protocol turns them into replayable, prefix-forkable cognitive model organisms. The methodological result is a continuous route from preserved symbolic activity to an intervention site and a differentiated response. The reference-strain analogy identifies what is held fixed. Brenner's N2 Bristol background and its documented stock history provide a biological example of a common experimental substrate. 12, 13 One frozen model configuration likewise identifies a background; it does not turn all generated records into independent specimens or remove the need to characterize variation. Template, task world, generated stream, answer slot and engineering replay remain distinct units.

Stage 4 expands observation across registered assignments, while expansion across model families would test portability across computational backgrounds.

Our operational adaptation of Koch-style reasoning concerns reproducible process investigation: locate an anomaly; prepare and retain the relevant symbolic history; intervene on a specified relation or context; and examine recurrence or change in newly prepared paths. These are research operations, not a claim that a cognitive feature is a microorganism or that a named human pathology has been established. The sequence can be revised as the preparation exposes its own failure conditions. Exact replay supports the preparation, contextual events identify candidate targets, and discriminatory interventions evaluate process models. The records show why these forms of evidence should remain separately inspectable.

We hypothesize that competing representations can organize successive operations differently: a correct value may remain available in the text while losing its task role. This account predicts selective preservation when a variable-referent relation is restored immediately before an observed rebinding, relative to equal-length irrelevant material. It would be challenged by equivalent relational outcomes after those manipulations or by a purely length-dependent response. A related hypothesis is that self-generated reconstructions act as new local task statements, transmitting an acquired reporting convention into variable use. The check16000 chronology supplies a candidate site; the fixed-prefix interventions establish an apparatus in which such a site can be tested.

Training-register capture is a further candidate model, not a recovered training record. In Stage 2, boxed output occurred in 19/32 formula trajectories compared with 3/68 other trajectories under the same cap. Some paths also attributed a nonexistent reporting instruction to the user or substituted a numerical objective for the decision. The proposed account predicts changes in task relations and rule attribution when algebraic presentation is manipulated while the task and report contract are held fixed. A decorative change alone would not establish capture. Each model may bring different learned conventions to a matching task surface; cross-model experiments can test that proposal without requiring a common phenotype in advance.

Every observational layer needs a measurement model when its readout is interpreted as cognitive content. Poldrack's analysis of reverse inference illustrates why an observable activation alone does not settle its cognitive meaning. 14 The same standard applies to our semantic codes. A frozen tokenizer specifies textual identity, not a context-invariant cognitive value for each token. Conditions, referents and subsequent use provide the process coordinates; interventions can constrain an interpretation without uniquely determining its implementation.

We stop at this symbolic plane because the team has not yet formulated a sufficiently specific attention-level hypothesis. A numerical activation does not interpret its own propositional content, and a readable passage does not reveal every process that produced it.

Our epistemic declaration is "Thinking refuses to be created." Here, creation means the exhaustive advance prescription of the process that will unfold. Human-language learning makes the generated stream intelligible through a shared symbolic vocabulary.
